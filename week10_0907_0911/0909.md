# Kubernetes

## 9. Packaging

- **helm 을 직접 생성**
    - 기본 구조
        - `Chart.yaml`: 메타 데이터 설정, 기본 정보 설정
        - `values.yaml`: 실제 채워질 값들에 대한 설정
        - `templates/`: 리소스들이 위치하는 디렉토리(deployment, service, pv, pvc, secret, ingress 등)
    - 디렉토리 생성 및 이동: `custom-mariadb`
    - `Chart.yaml` 파일 작성

        ```yaml
        apiVersion: v2
        name: custom-mariadb
        description: A custom Helm Chart
        type: application
        version: 0.1.0
        appVersion: "11.4"
        ```
    - 값을 채우는 `values.yaml`

        ```yaml
        image:
          repository: mariadb
          tag: "11.4"
          pullPolicy: IfNotPresent

        mariadb:
          rootPassword: "SecretRootPassword123!"
          database: "appdb"
          user: "appuser"
          password: "UserPassword123!"

        persistence:
          hostPath: "/data/mariadb"
          storageSize: "1Gi"
          nodeName: ""

        service:
          type: ClusterIP
          port: 3306
        ```

    - 비밀번호를 담을 secret 파일: `templates/secret.yaml`

        ```yaml
        # templates/secret.yaml
        apiVersion: v1
        kind: Secret
        metadata:
          name: {{ .Release.Name }}-secret
        type: Opaque
        stringData:
          mariadb-root-password: {{ .Values.mariadb.rootPassword | quote }}
          mariadb-password: {{ .Values.mariadb.password | quote }}
        ```

    - pv + pvc 저장소 관련 매니페스트: `templates/pv.yaml`

        ```yaml
        # templates/pv.yaml
        apiVersion: v1
        kind: PersistentVolume
        metadata:
          name: {{ .Release.Name }}-pv
          labels:
            app: {{ .Release.Name }}
        spec:
          capacity:
            storage: {{ .Values.persistence.storageSize }}
          accessModes:
          - ReadWriteOnce
          persistentVolumeReclaimPolicy: Retain
          storageClassName: manual
          hostPath:
            path: {{ .Values.persistence.hostPath }}
            type: DirectoryOrCreate
          # values.yaml 의 nodeName 이 설정된 경우에만 특정 노드에 고정
          {{- if .Values.persistence.nodeName }}
          nodeAffinity:
            required:
              nodeSelectorTerms:
              - matchExpressions:
                - key: kubernetes.io/hostname
                  operator: In
                  values:
                  - {{ .Values.persistence.nodeName }}
          {{- end }}
        ```

        ```yaml
        # templates/pvc.yaml
        apiVersion: v1
        kind: PersistentVolumeClaim
        metadata:
          name: {{ .Release.Name }}-pvc
        spec:
          accessModes:
          - ReadWriteOnce
          storageClassName: manual
          resources:
            requests:
              storage: {{ .Values.persistence.storageSize }}
        ```

    - deployment: `templates/deployment.yaml`
        - 비밀번호는 직접 넣지 않고 위에서 만든 secret 을 `secretKeyRef` 로 참조

        ```yaml
        # templates/deployment.yaml
        apiVersion: apps/v1
        kind: Deployment
        metadata:
          name: {{ .Release.Name }}
          labels:
            app: {{ .Release.Name }}
        spec:
          replicas: 1
          selector:
            matchLabels:
              app: {{ .Release.Name }}
          template:
            metadata:
              labels:
                app: {{ .Release.Name }}
            spec:
              containers:
              - name: mariadb
                image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
                imagePullPolicy: {{ .Values.image.pullPolicy }}
                ports:
                - containerPort: 3306
                env:
                - name: MARIADB_ROOT_PASSWORD
                  valueFrom:
                    secretKeyRef:
                      name: {{ .Release.Name }}-secret
                      key: mariadb-root-password
                - name: MARIADB_DATABASE
                  value: {{ .Values.mariadb.database | quote }}
                - name: MARIADB_USER
                  value: {{ .Values.mariadb.user | quote }}
                - name: MARIADB_PASSWORD
                  valueFrom:
                    secretKeyRef:
                      name: {{ .Release.Name }}-secret
                      key: mariadb-password
                volumeMounts:
                - name: data
                  mountPath: /var/lib/mysql
              volumes:
              - name: data
                persistentVolumeClaim:
                  claimName: {{ .Release.Name }}-pvc
        ```

    - service: `templates/service.yaml`

        ```yaml
        # templates/service.yaml
        apiVersion: v1
        kind: Service
        metadata:
          name: {{ .Release.Name }}-svc
        spec:
          type: {{ .Values.service.type }}
          selector:
            app: {{ .Release.Name }}
          ports:
          - protocol: TCP
            port: {{ .Values.service.port }}
            targetPort: 3306
        ```

    - 그 외 필요에 따라 추가하는 매니페스트: ingress, hpa, serviceAccount

- **템플릿 문법**
    - `{{ .Release.Name }}`: `helm install` 할 때 지정한 릴리스 이름
    - `{{ .Release.Namespace }}`: 설치되는 네임스페이스
    - `{{ .Chart.Name }}`, `{{ .Chart.Version }}`: `Chart.yaml` 의 값
    - `{{ .Values.xxx }}`: `values.yaml` 의 값 (`--set`, `-f` 로 덮어쓸 수 있음)
    - `| quote`: 값을 따옴표로 감싸줌(숫자나 true/false 가 문자열로 들어가야 할 때 필요)
    - `| default "값"`: 값이 비어있을 때 사용할 기본값
    - `{{- ... }}` / `{{ ... -}}`: 앞/뒤의 공백과 줄바꿈을 제거 → 렌더링 결과에 빈 줄이 남지 않도록
    - `{{- if 조건 }} ... {{- end }}`, `{{- range ... }} ... {{- end }}`: 조건 분기와 반복
    - `templates/_helpers.tpl`: 반복되는 이름이나 레이블을 named template 으로 정의하고 `{{ include "이름" . }}` 로 사용
    - `templates/NOTES.txt`: 설치가 끝난 뒤 화면에 출력되는 안내문
    - `_` 로 시작하는 파일과 `NOTES.txt` 는 쿠버네티스 리소스로 렌더링되지 않음

- **검증 및 배포**
    - 문법 검사: `helm lint custom-mariadb`
    - 렌더링 결과만 확인(실제 배포 X): `helm template my-db ./custom-mariadb`
    - 배포 직전 검증: `helm install my-db ./custom-mariadb --dry-run --debug`
    - 배포: `helm install my-db ./custom-mariadb`
    - 값을 바꿔서 배포
        - `helm install my-db ./custom-mariadb --set service.port=13306`
        - `helm install my-db ./custom-mariadb -f my-values.yaml`
    - 확인
        - `helm ls`
        - `kubectl get pods,svc,pv,pvc,secret`
    - 수정 후 반영: `helm upgrade my-db ./custom-mariadb`
    - 이력 확인 및 롤백
        - `helm history my-db`
        - `helm rollback my-db 1`
    - 삭제: `helm uninstall my-db`
        - 직접 만든 PV 는 `Retain` 정책이면 같이 삭제되지 않으므로 별도로 삭제

- **디렉토리 구조를 자동으로 생성해서 값만 변경해서 사용하는 것도 가능**: `helm create 이름`

    ```text
    echo/
    ├── Chart.yaml
    ├── values.yaml
    ├── charts/                    # 의존하는 하위 차트가 위치
    ├── .helmignore                # 패키징에서 제외할 파일
    └── templates/
        ├── deployment.yaml
        ├── service.yaml
        ├── ingress.yaml
        ├── hpa.yaml
        ├── serviceaccount.yaml
        ├── NOTES.txt
        ├── _helpers.tpl
        └── tests/
            └── test-connection.yaml
    ```


# Image Registry

## 1. Image Registry

### 1) 개요

- **이미지를 저장하는 장소**
- **public 레지스트리**
    - `Docker Hub`: 가장 방대한 생태계, 기본 설정없이 바로 사용 가능
    - `Git Hub Packages`: GitHub Action 과 연동해서 CI/CD 파이프라인 구축 용이
    - `public cloud 레지스트리`: AWS 의 ECR 이나 GCP 의 Artifact Registry 또는 RedHat 의 Quay.io 등에서 서비스를 제공
        - public 과 private 선택 가능
- **private 레지스트리**: 보안이나 비용 문제 때문에 서버를 직접 생성
    - `docker registry`: 가볍고 사용하기가 쉬움
    - `harbor`: 무거운 반면에 강력한 UI 기능을 제공

### 2) 동작 과정

- `build`: 이미지를 생성
- `태그 작업`: 레지스트리 구조에 맞게 이름을 변경
- `push`
- `pull`

## 2. Docker Hub

### 1) 도커 설치

### 2) docker hub 로그인

- `docker login`: 웹 브라우저가 열리게 되는데 여기서 로그인
- 브라우저를 쓸 수 없는 서버에서는 토큰으로 로그인
    - `docker login -u 계정 -p 토큰값`
    - 토큰은 Docker Hub → Account settings → Personal access tokens 에서 발급
    - 비밀번호 대신 토큰을 쓰는 이유: 권한(read/write/delete)을 제한할 수 있고 유출 시 해당 토큰만 폐기하면 됨
- 로그인 정보는 `~/.docker/config.json` 에 저장됨
- 로그아웃: `docker logout`

### 3) 이미지 이름과 태그

- 이미지이름: `Registry주소/레포지토리이름:태그`

- 설정: `docker tag 원본이미지 새이미지이름:태그`

- 도커 허브에 업로드 할 때는 Registry 주소가 없어도 된다.
    - Registry 주소를 생략하면 기본값인 `docker.io` 로 간주
- 태그를 생략하면 `latest` 가 적용되는데, 어떤 이미지인지 구분이 안 되므로 실제 배포에서는 버전 태그를 명시하는 것을 권장

### 4) 이미지 생성 및 push

- 애플리케이션 생성 및 테스트

    - `~/python_app` 디렉토리 안에서 작업
    - python 패키지 설치: `pip3 install flask --break-system-packages`

    - 소스 코드 작성: `app.py`

        ```py
        from flask import Flask
        app = Flask(__name__)
        @app.route('/')
        def hello():
            return "This is My Python Web Server"

        if __name__ == '__main__':
            app.run(host='0.0.0.0', port=5000)
        ```
    - 테스트: `python3 app.py`

- **이미지 생성 및 테스트**
    - Dockerfile 작성

        ```Dockerfile
        FROM python:3.9-slim

        WORKDIR /app

        RUN pip install flask

        COPY . .

        CMD ["python3", "app.py"]
        ```
    - 이미지 빌드
        - `docker build -t my-python-app .`
    - 이미지를 가지고 컨테이너를 만들어서 테스트: `docker run -d -p 5000:5000 my-python-app`

- **이미지 푸시**
    - 레포지토리 생성: `etakyung/python-app`
    - 태그 수정: `docker tag my-python-app etakyung/python-app:v1.0`
    - 이미지 푸시: `docker push etakyung/python-app:v1.0`
    - 이미지 테스트: `docker run -d -p 5000:5000 etakyung/python-app:v1.0`

- **쿠버네티스에서 가져와서 사용**

    - `deployment.yaml`

    ```yaml
    # deployment.yaml
    apiVersion: apps/v1
    kind: Deployment
    metadata:
      name: flask-deployment
      labels:
        app: flask-web
    spec:
      replicas: 3
      selector:
        matchLabels:
          app: flask-web
      template:
        metadata:
          labels:
            app: flask-web
        spec:
          containers:
          - name: flask-container
            image: etakyung/python-app:v1.0
            ports:
            - containerPort: 5000
    ```

    - `service.yaml`

        ```yaml
        apiVersion: v1
        kind: Service
        metadata:
          name: flask-service
        spec:
          type: ClusterIP
          selector:
            app: flask-web
          ports:
            - protocol: TCP
              port: 8080
              targetPort: 5000
        ```
    - `ingress.yaml`

        ```yaml
        apiVersion: networking.k8s.io/v1
        kind: Ingress
        metadata:
          name: ingress-nginx
          annotations:
            nginx.ingress.kubernetes.io/rewrite-target: /
            kubernetes.io/ingress.class: "nginx"
        spec:
          rules:
          - host: "my-flask-app.com"
            http:
              paths:
              - pathType: Prefix
                path: /
                backend:
                  service:
                    name: flask-service
                    port:
                      number: 8080
        ```

    - 배포 및 확인
        - `kubectl apply -f deployment.yaml -f service.yaml -f ingress.yaml`
        - `kubectl get pods,svc,ingress`
        - 파드가 `ImagePullBackOff` 나 `ErrImagePull` 이면 이미지 이름/태그 또는 인증 문제
        - 이미지 이름이 `계정/레포지토리:태그` 형태이므로 public 레포지토리는 별도 인증 없이 pull 가능
        - 도메인 접속 테스트를 위해 `/etc/hosts` 에 `인그레스컨트롤러IP my-flask-app.com` 추가

### 5) Private Repository 사용

- Docker Hub 에서는 계정 당 하나의 Private Repository 를 무료로 제공

- Private Repository 에 배포된 경우는 인증을 받아야만 Pull 이 가능

- Docker Hub 에서 Private Repository 를 생성: `etakyung/my-python-app`
- 이미지 태그 수정: `docker tag etakyung/python-app:v1.0 etakyung/my-python-app:v1.0`
- push: `docker push etakyung/my-python-app:v1.0`
- 도커 로그인이 되어있지 않으면 Private Repository 에 있는 것은 pull 을 할 수 없음
    - `docker logout` 후 `docker pull etakyung/my-python-app:v1.0` 을 하면 `pull access denied` 에러
- **쿠버네티스에서 Private image 사용**
    - 쿠버네티스는 노드의 `~/.docker/config.json` 을 쓰지 않기 때문에, 로컬에서 `docker login` 이 되어 있어도 별도의 Secret 이 필요
    - 인증용 Secret 생성
        - 타입은 `kubernetes.io/dockerconfigjson`
        - `kubectl create secret docker-registry 이름 --docker-server=https://index.docker.io/v1/ --docker-username=계정 --docker-password=토큰 --docker-email=이메일`
        - `kubectl create secret docker-registry regcred --docker-server=https://index.docker.io/v1/ --docker-username=etakyung --docker-password=토큰 --docker-email=taeyun1411@gmail.com`
        - 확인: `kubectl get secret regcred -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d`
        - Secret 은 네임스페이스 단위 리소스라서 파드를 배포하는 네임스페이스마다 만들어 주어야 함
    - deployment 에 추가
        - `spec.template.spec.imagePullSecrets` 에 위에서 만든 이름을 설정

            ```yaml
            # deployment.yaml
            apiVersion: apps/v1
            kind: Deployment
            metadata:
              name: flask-deployment
              labels:
                app: flask-web
            spec:
              replicas: 3
              selector:
                matchLabels:
                  app: flask-web
              template:
                metadata:
                  labels:
                    app: flask-web
                spec:
                  imagePullSecrets: # 여기가 추가됨
                  - name: regcred
                  containers:
                  - name: flask-container
                    image: etakyung/my-python-app:v1.0
                    ports:
                    - containerPort: 5000
            ```

    - 파드마다 적지 않고 ServiceAccount 에 붙여서 해당 SA 를 쓰는 모든 파드에 일괄 적용하는 방법도 있음
        - `kubectl patch serviceaccount default -p '{"imagePullSecrets":[{"name":"regcred"}]}'`

### 6) Helm Chart 업로드

- 샘플 헬름 차트를 생성: `helm create echo`
- 헬름 차트를 docker hub 에 업로드하기 위해서 helm 이 도커에 로그인이 되어있어야 한다.

    - `helm registry login registry-1.docker.io -u 계정`

- 디렉토리를 직접 업로드하지 않고 패키징을 해서 업로드
    - `helm package 차트디렉토리경로`
    - `helm package echo` → `echo-0.1.0.tgz` 가 생성 (`Chart.yaml` 의 name-version 으로 파일명이 결정)
- push: `helm push 패키지경로 oci://registry-1.docker.io/계정`
    - `helm push echo-0.1.0.tgz oci://registry-1.docker.io/etakyung`
    - Helm 3 부터 차트를 OCI 아티팩트로 취급해서 이미지 레지스트리에 그대로 저장할 수 있음 → 차트 전용 저장소를 따로 두지 않아도 됨
    - Docker Hub 에는 `계정/차트이름` 레포지토리가 생기고 태그는 차트 버전이 됨
- **업로드한 차트 사용**
    - 내용 확인: `helm show all oci://registry-1.docker.io/etakyung/echo --version 0.1.0`
    - 내려받기: `helm pull oci://registry-1.docker.io/etakyung/echo --version 0.1.0`
    - 바로 설치: `helm install my-echo oci://registry-1.docker.io/etakyung/echo --version 0.1.0`

## 3. Docker Registry

### 1) 개요

- Docker Hub 에서는 Private Registry 구축을 위한 registry 이미지를 제공하는데 이 이미지를 컨테이너로 실행하고 그 안에 이미지를 로컬에 저장하는 방식
- 단순 텍스트 방식만 제공하기 때문에 웹 기반의 검색하려면 GUI 인터페이스를 제공하는 다른 컨테이너와 결합해서 사용할 수 있음

### 2) Registry 생성

`docker run -d --name=이름 -p 포트번호:5000 registry:2`

- `docker run -d --name=registry -p 5000:5000 registry:2`
- 컨테이너 안(`/var/lib/registry`)에 이미지가 저장되므로, 컨테이너를 지우면 이미지도 같이 사라짐
    - 유지하려면 볼륨을 연결: `docker run -d --name=registry -p 5000:5000 -v /data/registry:/var/lib/registry registry:2`

### 3) 레지스트리 확인

- `curl -s http://IP:포트번호/v2/`
    - 정상이면 빈 JSON(`{}`) 이 응답됨
- 저장된 레포지토리 목록: `curl -s http://IP:포트번호/v2/_catalog`
- 특정 레포지토리의 태그 목록: `curl -s http://IP:포트번호/v2/레포지토리이름/tags/list`
- GUI 연결: `docker run -dit -p 포트번호:8080 --name 이름 --link 레지스트리이름 -e REGISTRY_URL=http://IP:포트번호/v2 -e REGISTRY_NAME=IP주소:포트번호 --restart=always hyper/docker-registry-web`
    - `docker run -dit -p 8080:8080 --name registry-web --link registry -e REGISTRY_URL=http://192.168.56.10:5000/v2 -e REGISTRY_NAME=192.168.56.10:5000 --restart=always hyper/docker-registry-web`

- **이미지 푸시**
    - 이미지 태그 작업: `docker tag 이미지 192.168.56.10:5000/레포지토리이름:태그`
        - `docker tag etakyung/python-app:v1.0 192.168.56.10:5000/pythonapp:v1`

    - **이미지 푸시 에러**
        - `docker push 192.168.56.10:5000/pythonapp:v1`
        - 푸시 에러
        - ImageRegistry 는 기본적으로 HTTPS 통신 만을 허용
    - **HTTP 를 사용할 수 있도록 설정 변경**
        - Docker 의 설정 파일인 `daemon.json` 파일에 HTTP 를 사용할 수 있도록 설정을 추가
        - 이 파일의 위치는 linux 의 경우는 `/etc/docker` 에 위치
        - `"insecure-registries" ["IP:포트번호"]`

            ```json
            {
            "insecure-registries":["192.168.56.10:5000"]
            }
            ```
        
    - 도커를 재시작: `sudo systemctl restart docker`
    - 컨테이너 다시 시작: 
        - `docker start registry`
        - `docker start registry-web`
    - 이미지를 다시 푸시: `docker push 192.168.56.10:5000/pythonapp:v1`

    - kubernetes 에서 사용하고자 하면 모든 노드 컴퓨터에 이 이미지 저장소를 사용할 수 있도록 설정을 해야 한다.
        - `/etc/containerd/config.toml` 파일에 내용을 추가

            ```text
            [plugins."io.containerd.grpc.v1.cri".registry.mirrors."192.168.56.10:5000"]
            endpoint=["http://192.168.56.10:5000"]
            ```
    - containerd 재시작
        - `sudo systemctl restart containerd`
    - 다시 배포
    - 노드에 추가 작업
        - `sudo mkdir -p /etc/containerd/certs.d/192.168.56.10:5000`
        - `sudo vim /etc/containerd/certs.d/192.168.56.10:5000/hosts.toml`
        - 작성

            ```text
            server = "http://192.168.56.10:5000"
            [host."http://192.168.56.10:5000"]
              capabilities = ["pull", "resolve"]
              skip_verify = true
            ```
    - `/etc/containerd/config.toml` 파일에 내용을 수정

        ```text
        [plugins."io.containerd.grpc.v1.cri".registry]
        config_path = "/etc/containerd/certs.d"
        ```

    - containerd 재시작
        - `sudo systemctl restart containerd`
    - 워커 노드에서 테스트 하고자 하는 경우
        - `sudo crictl pull 이미지경로`
        - `sudo crictl pull 192.168.56.10:5000/pythonapp:v1`
    - 정리
        - 이미지를 **push** 하는 쪽(도커)은 `/etc/docker/daemon.json` 의 `insecure-registries` 설정
        - 이미지를 **pull** 하는 쪽(쿠버네티스 노드의 containerd)은 `/etc/containerd/` 설정
        - 설정은 마스터/워커 **모든 노드**에 동일하게 적용해야 함(파드가 어느 노드에 뜰지 모르기 때문)

## 4. harbor

### 1) 개요

- 내부에서 Docker 이미지와 Helm Chart 같은 배포 패키지를 안전하게 저장하고 관리하는 private registry

### 2) 사용하는 이유

- 내부 이미지를 안전하게 관리하기 위해서
- Docker Hub 장애나 인터넷 문제 영향 감소
- harbor 는 이미지의 취약점을 검사하는 기능을 제공
- 오픈 소스: 무료
    - Docker Hub 나 Cloud 저장소는 일정 부분 이상 사용하면 비용을 지불
- Web UI 도 제공

### 3) 주요 기능

- `프로젝트` 단위로 이미지를 묶어서 관리하고 public/private 지정 가능
- 사용자/그룹별 권한 관리(RBAC), LDAP·OIDC 연동
- 취약점 스캔(Trivy) 및 스캔 결과에 따라 pull 차단 정책 설정 가능
- 이미지 서명(Notary/Cosign)으로 신뢰할 수 있는 이미지만 배포
- 복제(Replication): 다른 레지스트리(Docker Hub, 다른 Harbor 등)와 이미지 동기화
- 가비지 컬렉션, 태그 보존(Retention) 정책으로 저장 공간 관리
- Docker 이미지뿐 아니라 Helm Chart 도 OCI 아티팩트로 저장 가능

### 4) 설치

- Docker 와 docker compose 가 필요
- 오프라인/온라인 설치 패키지를 받아서 `harbor.yml` 에 호스트 이름과 인증서 경로, 관리자 비밀번호를 설정한 뒤 `install.sh` 실행
- 여러 컨테이너(core, registry, database, redis, portal, jobservice 등)가 함께 기동됨
- 기본 관리자 계정: `admin`

# Git

## 1. 버전 관리 시스템

### 1) 개요

- 파일의 변화를 시간에 따라 기록한 후 과거 특정 시점의 버전을 다시 불러올 수 있는 시스템
- 모든 컴퓨터 파일이 버전 관리의 대상

### 2) 종류

- **로컬 버전 관리 시스템**
    - 직접 백업하지 않고 로컬 데이터베이스에 변경 사항을 기록해 두는 방식
    - 각 리비전들 간의 `patch set` 이라고 하는 데이터의 차이점을 특수한 형태의 파일에 보관하는 방식으로 특정 시점의 파일 내용을 확인하고자 하는 경우는 원본 파일에 `patch set` 을 전부 더해서 파일을 만들어내는 방식
    - Mac OS X 에서는 개발 도구를 설치하면 RCS 가 자동으로 설치되는데 RCS 가 대표적인 로컬 버전 관리 시스템
    - 내 컴퓨터에만 이력이 남기 때문에 협업에는 이용할 수 없음

- **중앙 집중식 버전 관리 시스템(클라이언트-서버 모델)**
    - 하나의 서버에 변경 내역을 전부 기록해두고 여러 클라이언트가 접속해서 변경 내용을 적용하는 방식
    - 서버에 장애가 발생하면 모든 것이 잘못됨
    - CVS, Subversion, Perforce 가 대표적인 도구

- **분산 버전 관리 시스템**
    - 저장소를 통째로 복사해서 서버와 클라이언트 모두 가지고 있는 방식
    - 체크아웃을 할 때마다 전체 백업이 수행
    - Git(리눅스 커널 개발을 위해 Linus Torvalds 가 처음 개발), Mercurial(구글이 파이썬으로 개발), Bazaar, Darcs 등이 대표적인 도구
    - 원격 저장소에 장애가 나도 각자의 로컬 저장소로 복구가 가능

## 2. git

### 1) 개요

- 컴퓨터 파일의 변경 사항을 추적하고 여러 명의 사용자들 간에 해당 파일들의 작업을 조율하기 위한 버전 관리 시스템 또는 이를 위한 명령어

- Open Source
- **장점**
    - 이력 기록 및 추적
    - 전 세계 많은 사용자가 이용
    - 분산 버전 관리 시스템이어서 원격 저장소에 문제가 발생해도 로컬 저장소를 이용해서 복원 가능
    - 변경 이력 병합 가능

### 2) Cloud Service

- **GitHub**
    - Ruby on Rails 로 작성된 분산 버전 관리 툴인 git 의 원격 저장소 호스팅 서비스
    - 영리적인 서비스와 오픈 소스를 위한 무상 서비스를 모두 제공
    - git 이 텍스트 명령어 방식인데 github 은 GUI를 제공
    - github 은 pastebin(텍스트 데이터를 저장하고 공유할 수 있는 온라인 저장소) 과 유사한 Gist 와 Wiki 를 Repository 마다 운영하고 있으며 git 저장소를 통해 고칠 수 있음
    - git 프로젝트 저장소 이외에 github action 과 github deployment API 를 이용해서 CI/CD 를 구현할 수 있고 Project Boards 를 이용해서 협업도 가능하면 정적 웹 페이지 배포가 가능하고 도커 이미지 저장소로도 사용할 수 있음
    - public 저장소는 무료인데 private 저장소는 3인 이하인 경우는 무료이고 설치형 버전인 Enterprise 는 유료

- **GitLab**
    - private 저장소를 참여 인원 수에 상관없이 무제한으로 생성 가능
    - 로컬 서버 시스템으로 사용 가능
    - 저장소의 최대 용량이 5GB
    - Github 보다 체계적인 이슈 트래커 기능과 CI 서비스를 제공

- **BitBucket**
    - 이슈 관리 시스템인 Jira 를 만든 Atlassian 이 만든 서비스
    - 5명 이하인 경우는 무료이고 그 이상에 비용을 지불

### 3) Remote Repository & Local Repository

- `Remote Repository`: 전용 서버의 저장소
- `Local Repository`: 사용하고 있는 컴퓨터의 저장소

### 4) git 설치

- **git 설치**
    - `git-scm.com/downloads` 에서 다운로드 받아서 설치
    - Linux 에서는 `git` 이라는 패키지를 설치
    - 설치 확인: `git --version`
- **github CLI 명령어를 편리하게 사용하기 위해서 `gh` 를 설치하는 경우가 있음**
    - 설치 확인: `gh --version`
- GUI 환경에서 편리하게 작업하기 위해서 `sourcetree` 를 설치하기도 한다. 

- **기본 브랜치 이름을 변경**
    - git 의 기본 브랜치 이름은 `master`
    - github 의 기본 브랜치 이름은 `main`
        - 그대로 두면 로컬은 master, 원격은 main 이 되어 push 할 때 브랜치가 어긋남
    - 기본 브랜치 이름을 main 으로 수정: `git config --global init.defaultBranch main`
    - 이미 만들어진 저장소의 브랜치 이름 변경: `git branch -m master main`

- **사용자 정보 설정**
    - 현재 프로젝트에만 적용
        - `git config user.name 이름`
        - `git config user.email 이메일`
    - 전체 프로젝트에 적용
        - `git config --global user.name 이름`
        - `git config --global user.email 이메일`
    - 확인
        - `git config --global user.name`
        - `git config --global user.email`
        - 전체 설정 확인: `git config --list`
    - 전역 설정은 `~/.gitconfig`, 프로젝트 설정은 `저장소/.git/config` 에 저장되고 프로젝트 설정이 우선 적용됨

### 5) 기본 개념

- **작업 영역**
    - `Working Directory`
        - 이력 관리 대상(tracked) 파일들이 위치하는 영역
        - 저장소 디렉토리에서 .git 디렉토리를 제외한 공간
        - 작업 중인 파일이나 코드가 저장되는 공간
        - Work Tree 라고도 함
        - .git 디렉토리를 제외한 모든 공간

    - `Staging Area`
        - 이력을 기록할 대상 파일들이 위치하는 영역
        - Index 라고도 함
        - .git 디렉토리 하위에 파일 형태로 존재

    - `Local Repository`
        - 이력이 기록된 파일들이 위치하는 영역
        - .git 디렉토리에 이력 관리를 위한 모든 정보가 저장되고 관리됨
    - **명령어**
        - Working Directory 에서 Staging Area 로 이동시키는 명령: `git add`
        - Staging Area 에서 Local Repository 로 이동시키는 명령: `git commit`
        - Local Repository 에서 Remote Repository 로 복사하는 명령: `git push`

- **Commit**
    - 파일 및 디렉토리의 추가/변경 사항을 로컬 저장소에 기록하는 것이 `Commit`
    - Commit 을 수행하면 이전 Commit 부터 현재 상태까지의 변경 이력이 기록된 `Revision` 이 생성됨
    - 순서대로 저장되므로 최근 Commit 부터 올라가면 과거 변경 이력과 내용을 알 수 있음
    - Revision 은 40자리의 고유한 이름(SHA-1 해시)을 가지고 있는데 화면에 보여질 때는 앞의 7자리 정도만 짧게 보여지고 이 짧은 이름을 가지고 작업이 가능
    - **Commit 을 할 때는 메시지를 작성해야 하는데 권장 사항**
        - 첫 번째 줄은 Commit 내의 변경 내용을 요약
        - 두 번째 줄은 빈줄
        - 세 번째 줄은 변경한 이유

- **Working Directory 에서 관리되는 파일의 상태**
    - `Modified`: 관리 중인 파일에 수정 사항이 감지되었지만 커밋이 되지 않은 상태
    - `Staged`: 감지된 파일의 수정 사항이 Staging Area 로 이동한 상태
    - `Committed`: 파일의 수정 사항에 대한 이력을 저장한 상태
    - `Untracked`: 저장소에서 관리하지 않는 파일
    - 상태 변화 흐름

        ```text
        Untracked --(git add)--> Staged --(git commit)--> Committed
                                                              |
                                              파일 수정 시 --> Modified --(git add)--> Staged
        ```
    - 현재 상태 확인: `git status`
    - 관리 대상에서 제외할 파일은 `.gitignore` 에 작성
        - 빌드 결과물, 로그, 비밀번호나 토큰이 들어있는 설정 파일 등
        - 이미 tracked 상태가 된 파일은 `.gitignore` 에 추가해도 계속 추적되므로 `git rm --cached 파일` 로 먼저 빼야 함
