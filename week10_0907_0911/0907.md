## 8. Health Check

### 8) 초기화 컨테이너

- **개요**
    - 파드 내부에서 메인이 되는 컨테이너를 기동하기 전에 별도의 컨테이너를 기동하기 위한 기능
    - 설정에 관련된 내용을 가지는 컨테이너
    - 설정과 메인 컨테이너를 분리

    - 설정과 메인 컨테이너를 분리 - 설정에 필요한 스크립트 등을 메인 컨테이너에 보관하지 않고 상태를 유지할 수 있음
    - 보안을 유지하고 이미지 크기를 줄일 수 있음
    - 설정은 `spec.initContainers` 에 복수로 지정할 수 있고 위에서부터 하나씩 순서대로 적용
    - `spec.containers` 에 여러 개의 컨테이너를 배치하면 병렬로 기동이 된다. 순서 제어가 어려움

- **nginx 이미지를 이용한 초기화 컨테이너 실습**
    - 연습은 pod, 실제로는 Deployment
    - 매니페스트 파일: `sample-initcontainer.yaml`

        ```yaml
        apiVersion: v1
        kind: Pod
        metadata:
          name: sample-initcontainer
        spec:
          initContainers:
            - name: output-1
              image: alpine:latest
              command: ['sh', '-c', 'sleep 20; echo 1st > /usr/share/nginx/html/index.html']
              volumeMounts:
              - name: html-volume
                mountPath: /usr/share/nginx/html/
            - name: output-2
              image: alpine:latest
              command: ['sh', '-c', 'sleep 20; echo 2nd > /usr/share/nginx/html/index.html']
              volumeMounts:
              - name: html-volume
                mountPath: /usr/share/nginx/html/
          containers:
            - name: nginx-container
              image: nginx:latest
              volumeMounts:
              - name: html-volume
                mountPath: /usr/share/nginx/html/
          volumes:
            - name: html-volume
              emptyDir: {}
        ```
    - 파드의 상태를 실시간으로 감시: `kubectl get pods -w`
    - 리소스 배포: `kubectl apply -f sample-initcontainer.yaml`
    - 추가된 파일 확인: `kubectl exec -it sample-initcontainer -- cat /usr/share/nginx/html/index.html`

### 9) 컨테이너 기동 직후와 종료되기 전에 작업을 수행

- `spec.containers[].lifecycle.preStop` 이나 `postStart` 에 간단한 명령 수행을 지정하는 것이 가능
- 매니페스트 파일: `sample-lifecycle-exec.yaml`

    ```yaml
    apiVersion: v1
    kind: Pod
    metadata:
      name: sample-lifecycle-exec
    spec:
      containers:
        - name: nginx-container
          image: nginx:latest
          command: ["/bin/sh", "-c", "touch /tmp/started; sleep 300"]
          volumeMounts:
          - name: html-volume
            mountPath: /usr/share/nginx/html/
          lifecycle:
            postStart:
              exec:
                command: ["/bin/sh", "-c", "sleep 20; touch /tmp/poststart"]
            preStop:
              exec:
                command: ["/bin/sh", "-c", "touch /tmp/prestop; sleep 20"]
      volumes:
        - name: html-volume
          emptyDir: {}
    ```
- 배포: `kubectl apply -f sample-lifecycle-exec.yaml`
- 바로 확인: `kubectl exec -it sample-lifecycle-exec -- ls /tmp`
- 20초 후에 확인: `kubectl exec -it sample-lifecycle-exec -- ls /tmp`
- 삭제: `kubectl delete -f sample-lifecycle-exec.yaml`
- 확인: `kubectl exec -it sample-lifecycle-exec -- ls /tmp`

- 이 부분을 변경하면 웹 요청 가능

```yaml
exec:
  command: ["/bin/sh", "-c", "touch /tmp/prestop; sleep 20"]

httpGet:
  path: 경로
  port: 포트번호
  host: 도메인
  scheme: HTTP 또는 HTTPS
```

- **주의할 점**
    - `postStart` 에는 타임 아웃 설정을 할 수 없는데 `postStart` 실행 중에는 Probe 도 실행되지 않기 때문에 `postStart` 에서 Dead Lock 이 발생해서 멈추게 되면 복구 방법이 없으므로 `postStart` 명령어 안에 타임아웃 설정을 해주어야 한다.
    - 재시도 매커니즘이 없기 때문에 쿠버네티스는 종료시킨 뒤 재시작 정책을 따르게 됨
    - Probe 는 컨테이너가 실행되는 동안 주기적으로 상태를 체크하지만 `postStart` 는 단 한 번만 실행된다. 

- **사용하는 경우**
    - 초기화 신호: 컨테이너가 시작되었음을 외부 모니터링 시스템이나 로드밸런서에 알릴 때 
    - 데이터 워밍업: 앱이 시작되자마자 특정 캐시를 채우도록 내부 API를 호출할 때 

### 10) 삭제

- 상위 리소스가 삭제되면 하위 리소스를 삭제하기 위해 `Garbage Collection`을 수행
- **레플리카 셋을 삭제할 때의 동작**
    - `Background(기본값)`: 레플리카셋을 삭제하고 파드는 Garbage Collection 이 비동기적으로 삭제
    - `Foreground`: 레플리카셋을 먼저 삭제하지 않고 파드를 먼저 삭제하고 파드가 전부 삭제되면 레플리카셋을 삭제
    - `Orphan`: 레플리카셋만 삭제

- kubectl 로 설정할 수 있는 옵션은 `Background` 와 `Orphan` 뿐이며 `Foreground` 로 삭제하려면 API 를 조작
- 옵션 설정은 삭제할 때 `--cascade=background` 또는 `orphan` 을 설정

### 11) Update 전략

- **개요**
    - 애플리케이션이 변경될 때 어떻게 업데이트를 수행할 것인지 
    - 기본 전략은 RollingUpdate

- **recreate 전략**
    - 모든 버전의 파드를 전부 삭제하고 한꺼번에 생성하는 방식
    - `spec.strategy.type` 에 `Recreate` 를 설정하면 된다.
    - 매니페스트 생성: `sample-deployment-recreate.yaml`

        ```yaml
        apiVersion: apps/v1
        kind: Deployment
        metadata:
          name: sample-deployment-recreate
        spec:
          strategy:
            type: Recreate
          replicas: 3
          selector:
            matchLabels:
              app: sample-app
          template:
            metadata:
              labels:
                app: sample-app
            spec:
              containers:
              - name: nginx-container
                image: nginx
        ```
    - 파드의 상태 감시: `kubectl get pods -w`
    - 배포: `kubectl apply -f sample-deployment-recreate.yaml`
        - 파드가 한꺼번에 만들어지는 것처럼 보여진다. 
    - 업데이트 하기 위해서 매니페스트 이미지 버전을 변경
        - `image:nginx:1.17`
    - 업데이트 적용

- **RollingUpdate**
    - **개요**
        - 새 버전의 애플리케이션을 배포할 떄 새 버전의 애플리케이션은 하나씩 늘려가고 기존 버전의 애플리케이션은 하나씩 줄여나가는 방식
        - kubernetes 의 표준 배포 방식
        - 새로운 버전으로 배포된 Pod 에 문제가 생기면 다시 이전 버전의 Pod 로 서비스를 대체할 수 있어서 상당히 안정적인 배포 방식이지만 업데이트가 느리게 진행되는 단점이 있다. 
    - **설정 값**
        - `maxSurge`
            - 한 번에 생성할 수 있는 최대 파드 개수
            - % 또는 개수로 설정
            - 설정하지 않을 경우 기본값은 25%

        - `maxUnavailable`
            - 한 번에 삭제할 파드 개수
            - 높게 설정하면 배포를 빠르게 할 수 있음
            - 너무 높게 설정하면 트래픽이 남아있는 파드에 집중될 수 있어서 주의
            - % 또는 개수로 설정
            - 설정하지 않을 경우 기본값은 25%
    - 매니페스트 파일: `sample-deployment-rollingupdate.yaml`

        ```yaml
        apiVersion: apps/v1
        kind: Deployment
        metadata:
          name: sample-deployment-rollingupdate
        spec:
          strategy:
            type: RollingUpdate
            rollingUpdate:
              maxUnavailable: 0
              maxSurge: 1
          replicas: 3
          selector:
            matchLabels:
              app: sample-app
          template:
            metadata:
              labels:
                app: sample-app
            spec:
              containers:
              - name: nginx-container
                image: nginx
        ```

    - 배포
    - 파드 실시간 감지
    - 이미지 변경: `kubectl set image deployment sample-deployment-rollingupdate nginx-container=nginx:1.17`

- **DaemonSet 의 업데이트 전략: `OnDelete & RollingUpdate`**

    - `OnDelete`
        - 매니페스트를 수정해서 이미지 등을 변경해도 기존 파드가 업데이트되지 않음
        - 운영 상 정지되면 안되는 파드이거나 업데이트가 급하게 필요하지 않은 경우 사용하는데 이전 버전이 장기간 남아있는 형태
        - 업데이트는 다음 번에 다시 생성하거나 수동으로 파드를 삭제하면 이루어진다.
    - `RollingUpdate`
        - maxSurge 설정이 안됨

- **StatefulSet 의 업데이트 전략: `OnDelete & RollingUpdate`**
    - `DaemonSet` 과 동일하게 동작
    - 저장소를 사용하기 때문

- **RollingUpdate 를 이용해서 안전하게 애플리케이션을 중지하고 파드를 삭제**
    - `RollingUpdate` 는 차례로 파드를 중지하고 새로운 파드로 교체하는 동작을 수행하는데 파드를 삭제할 때는 주의해야 할 점이 있는데 파드의 컨테이너가 삭제될 때 클라이언트가 `HTTP/HTTPS` 요청을 처리 중이라면 기대한 응답을 받을 수 없을 수도 있다.
    - 데이터 스토어라면 종료까지 어느 정도 시간이 걸릴 때도 있기 때문에 종료 처리가 되지 않은 상황에서 파드가 삭제될 수 있음
    - 애플리케이션을 안전하게 중지하고 파드 내부의 컨테이너가 삭제되도록 하는 것이 중요한데 `Graceful Shutdown` 이라고 한다. 
    - 파드에 종료 명령을 내리면 파드에 속하는 컨테이너 프로세스에는 `SIGTERM` 이 전송되는데 `SIGTERM` 을 받은 컨테이너는 `terminationGracePeriodSeconds` 로 설정된 시간 이내에 애플리케이션이 종료되지 않으면 `SIGKILL` 이 전송되고 컨테이너는 강제로 종료됨
    - 종료 처리에 시간이 걸릴 것 같은 컨테이너는 `terminationGracePeriodSeconds` 값을 길게 설정

    - nginx 는 `SIGTERM` 을 받으면 곧바로 종료를 하는데 nginx 는 `worker` 프로세스를 가지고 동작을 하므로 이 또한 안전하게 종료해야 함
    - nginx 는 `preStop` 항목에서 `quit` 를 수행하도록 해야한다. 

        ```yaml
        spec:
          containers:
          - name: nginx
            image: nginx
            ports:
            - containerPort: 80
            lifecycle:
              preStop:
                exec:
                  command:
                  - "bin/sh"
                  - "-c"
                  - "nginx -s quit"
        ```

- **Blue-Green Update**
    - **개요**
        - `RollingUpdate` 는 이전 버전과 새로운 버전이 같이 존재하는 시간이 발생하는데 이 특성은 애플리케이션의 사용자나 다른 프로그램에 의해 의도하지 않은 부작용이 발생할 수 있음
        - 기존 버전과 세로운 버전을 동시에 운영하는 방식
        - 서비스 목적으로는 새버전의 Pod 만 가능하고 이전 버전의 파드는 테스트 목적으로만 접속하도록 하는 방식
        - 새로운 버전에 문제가 생기면 기존 파드로 서비스를 수행
        - `blue-green` 업데이트는 배포시 기존에 배포된 서버 그룹과는 별도로 새로운 애플리케이션을 배포할 서버 그룹을 준비하고 로드 밸런서와 디스커버리 레벨에서 참조 대상을 교체해서 배포하는 방법

        - `blue/green` 업데이트를 이용해서 애플리케이션을 배포할 때는 `version` 으로 구분해서 관리
        - green 배포용 yaml 파일을 할 때 이전 버전의 yaml 파일과 내용은 같지만 사용하는 이미지의 경로와 labels 의 `version` 만 수정해서 배포
    - 블루 버전의 매니페스트: `print-version-blue.yaml`

        ```yaml
        apiVersion: apps/v1
        kind: Deployment
        metadata:
          name: print-version-blue
          labels:
            app: print-version
            color: blue
        spec:
          replicas: 1
          selector:
            matchLabels:
              app: print-version
              color: blue
          template:
            metadata:
              labels:
                app: print-version
                color: blue
            spec:
              containers:
              - name: print-version
                image: ghcr.io/jpubdocker/print-version:v0.0.1
                ports:
                - containerPort: 8080
        ```
    - green 버전의 매니페스트: `print-version-green.yaml`

        ```yaml
        apiVersion: apps/v1
        kind: Deployment
        metadata:
          name: print-version-green
          labels:
            app: print-version
            color: green
        spec:
          replicas: 1
          selector:
            matchLabels:
              app: print-version
              color: green
          template:
            metadata:
              labels:
                app: print-version
                color: green
            spec:
              containers:
              - name: print-version
                image: ghcr.io/jpubdocker/print-version:v0.0.2
                ports:
                - containerPort: 8080
        ```
    - 2 개의 매니페스트 배포

    - 서비스 매니페스트: `print-version-service-color.yaml`

        ```yaml
        apiVersion: v1

        metadata:
          name: print-version

            app: print-version

          ports:
          - port: 80

            app: print-version
        ```

    - 서비스 배포: `kubectl apply -f print-version-service-color.yaml`

- **Canary 업데이트**    
    - **개요**
        - Blue/Green 방식보다 진보된 업데이트 방식
        - 애플리케이션의 몇몇 새로운 기능을 테스트할 때 사용
        - 2개의 버전을 모두 배포하지만 새 버전의 트래픽을 조금씩 늘려가는 방식
        - 새로운 버전에 아무런 문제가 없다면 이전 버전은 모두 삭제하고 새로운 버전으로 대체하는 방식
        - 여러 개의 버전에 동시에 존재하기 때문에 세션을 유지해 주어야 하는 경우 sticky session 을 이용해서 동일한 서버에 접근하도록 해주어야 한다. 
    - **가장 단순한 방식의 구현**
        - 다른 버전의 파드를 일정한 비율로 replicaset 으로 배포한 후 동일한 서비스에 연결

    - **nginx ingress controller 의 Annotations 기능을 이용: 권장**
        - nginx 인그레스 컨트롤러에서는 canary update 를 위해서 일정 비율의 트래픽만 인그레스로 분산하는 것이 가능
            ```yaml
            apiVersion: networking.k8s.io/v1
            kind: Ingress
            metadata:
              name: 이름
              annotations:
                nginx.ingress.kubernetes.io/canary: "true"
                nginx.ingress.kubernetes.io/canary-weight: "비율"
            ```

    - **Argo Rollouts 를 이용하는 방식: 현업에서 가장 많이 사용하는 방식**
        - 자동화된 방식

            ```yaml
            apiVersion: argoproj.io/v1alpha1
            kind: Rollout
            metadata:
              name: my-app-rollout
            spec:
              replicas: 10
              strategy:
                canary:
                  steps:
                  - setWeight: 10 # 10% 배포 후 대기
                  - pause:{duration: 1h} # 1시간 동안 모니터링
                  - setWeight: 50 # 이상이 없으면 50% 로 확대
                  - pause: {} # 수동 승인 대기
            ```
    - **선택**
        - 테스트용: Service Selector 이용
        - 운영환경인데 가중치 조절이 필요한 경우: `Ingress Annotations`
        - 대규모 자동화된 배포 파이프라인: `Argo Rollouts`

- **업데이트 관련 상세 파라미터**
    - `minReadySeconds`: 파드가 완전히 기동되었다고 판단하는 시간
    - `revistionHistoryLimit`: 롤백이 가능한 이력의 수 설정
    - `progressDeadlineSeconds`: Recreate/RollingUpdate 처리 타임아웃 시간으로 이 시간이 경과하면 자동으로 롤백
