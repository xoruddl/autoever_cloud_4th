### 12) Ingress

- 로컬 쿠버네티스에서 내부 Ingress 를 사용하기 위해서 필요한 준비 사항
    - MetalLB 를 설치해서 LoadBalancer 를 사용할 수 있는 상태
    - Nginx Ingress Controller 를 설치

- 2개의 디플로이먼트를 Ingress 를 이용해서 배포
    - 디플로이먼트와 서비스를 위한 매니페스트(`ingress-resource.yaml`)

    ```yaml
    apiVersion: apps/v1
    kind: Deployment
    metadata:
      name: backend1
    spec:
      replicas: 2
      selector:
        matchLabels:
          app: backend1
      template:
        metadata:
          labels:
            app: backend1
        spec:
          containers:
          - name: backend1
            image: nginxdemos/nginx-hello:plain-text
            ports:
            - containerPort: 8080
    ---
    apiVersion: v1
    kind: Service
    metadata:
      name: backend1-svc
    spec:
      ports:
      - port: 80
        targetPort: 8080
        protocol: TCP
        name: http
      selector:
        app: backend1
    
    ---
    apiVersion: apps/v1
    kind: Deployment
    metadata:
      name: backend2
    spec:
      replicas: 2
      selector:
        matchLabels:
          app: backend2
      template:
        metadata:
          labels:
            app: backend2
        spec:
          containers:
          - name: backend2
            image: nginxdemos/nginx-hello:plain-text
            ports:
            - containerPort: 8080
    
    ---
    apiVersion: v1
    kind: Service
    metadata:
      name: backend2-svc
    spec:
      ports:
      - port: 80
        targetPort: 8080
        protocol: TCP
        name: http
      selector:
        app: backend2
    ```
    - 배포: `kubectl apply -f ingress-resource.yaml`
    - 확인: `kubectl get pods, services`
    - Host 기반 Ingress Controller 라우팅 설정 매니페스트 생성(`ingress-test.yaml`)

    ```yaml
    apiVersion: networking.k8s.io/v1
    kind: Ingress
    metadata:
      name: ingress-nginx
      annotations:
        nginx.ingress.kubernetes.io/rewrite-target: /
        kubernetes.io/ingress.class: "nginx"
    spec:
      rules:
      - host: "example1.com"
        http:
          paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: backend1-svc
                port:
                  number: 80

        http:
          paths:
          - path: /
    ```

## 5. Config & Storage API

### 0) 개요

- 설정 파일 그리고 기밀 정보 등을 추가하거나 영구 볼륨을 제공하기 위한 리소스
- **종류**
    - `Secret`
    - `Config Map`
    - `PVC(Persistent Volume Claim)`

### 1) 환경 변수

- **개요**
    - 쿠버네티스에서 개별 컨테이너의 설정 내용은 환경 변수를 이용하거나 파일이 저장되어 있는 영역을 마운트하여 전달하는 것이 일반적

    - 쿠버네티스에서 환경 변수를 전달할 때는 파드 템플릿에 `env` 또는 `envFrom` 을 지정
    - **환경 변수에 포함시키는 정보**
        - 정적 설정: 데이터베이스의 위치나 서비스 이름 등
        - 파드 정보
        - 컨테이너 정보
        - 시크릿 리소스 기밀 정보
        - 컨피그맵 리소스 설정값

- **정적 설정을 위한 환경 변수**
    - 매니페스트 파일(`sample-env.yaml`)

        ```yaml
        apiVersion: v1
        kind: Pod
        metadata:
          name: sample-env
          labels:
            app: sample-app
        spec:
          containers:
          - name: nginx-container
            image: nginx:1.17
            env:
            - name: MAX_CONNECTION
              value: "100"
            - name: TZ
              value: Asia/Seoul
        ```
    - 배포: `kubectl apply -f sample-env.yaml`
    - 확인
        - `kubectl exec -it sample-env -- /bin/bash`
        - `kubectl exec -it sample-env -- env`

            ```bash
            MAX_CONNECTION=100
            TZ=Asia/Seoul
            ```
- **파드 정보**
    - 어떤 노드에서 파드가 기동하고 있는지와 파드 자신의 IP 주소, 기동 시간 등 파드에 관한 정보를 `fieldRef` 를 사용하면 참조할 수 있는데 확인 가능한 값은 `kubectl get pods -o yaml` 등으로 확인
    - 파드 정보 확인: `kubectl get pods sample-env -o yaml`
    - 파드 정보를 환경 변수로 사용
    - 매니페스트 파일(`sample-env-pod.yaml`)

        ```yaml
        apiVersion: v1
        kind: Pod
        metadata:
          name: sample-env-pod
          labels:
            app: sample-app
        spec:
          containers:
          - name: nginx-container
            image: nginx:1.17
            env:
            - name: K8S_NODE
              valueFrom:
                fieldRef:
                  fieldPath: spec.nodeName
        ```
    
    - 배포: `kubectl apply -f sample-env-pod.yaml`
    - 확인: `kubectl exec -it sample-env-pod -- /bin/bash`

- **컨테이너 정보**
    - 컨테이너 정보는 `resourceFieldRef` 를 사용하여 확인 가능
    - 컨테이너 정보를 환경 변수에 저장하는 매니페스트(`sample-env-container.yaml`)

        ```yaml
        apiVersion: v1
        kind: Pod
        metadata:
          name: sample-env-container
          labels:
            app: sample-app
        spec:
          containers:
          - name: nginx-container
            image: nginx:1.17
            env:
            - name: CPU_REQUESTS
              valueFrom:
                resourceFieldRef:
                  containerName: nginx-container
                  resource: requests.cpu
            - name: CPU_LIMITS
              valueFrom:
                resourceFieldRef:
                  containerName: nginx-container
                  resource: limits.cpu
        ```

- **환경 변수를 사용할 떄 주의할 점**
    - 쿠버네티스에서 command 나 args 로 실행할 명령어를 지정하는데 매니페스트에 작성된 환경 변수를 사용할 때 `${환경변수}` 로 하면 안되고 `$(환경변수)` 로 해야 한다.
    - 명령어에 잘못 지정한 환경 변수(`sample-env-fail.yaml`)

        ```yaml
        apiVersion: v1
        kind: Pod
        metadata:
          name: sample-env-fail
          labels:
            app: sample-app
        spec:
          containers:
          - name: nginx-container
            image: nginx:1.17
            command: ["echo"]
            args: ["${TESTENV}", "${HOSTNAME}"]
            env:
            - name: TESTENV
              value: "100"
        ```
    - command 나 args 는 매니페스트 내에서 만든 환경변수에만 접근이 가능
        - 운영체제에서 접근 가능한 환경 변수는 별도의 스크립트 파일을 만들어서 처리를 해야 한다.
            ```bash
            etakyung@k8s-master:~/kubernetes$ kubectl logs sample-env-fail
            100 $(HOSTNAME)
            ```

### 2) Secret

- **기밀 정보를 전달하는 방법**
    - **도커 빌드 시 컨테이너 이미지에 추가**
        - 이미지를 빌드할 떄 애플리케이션 측이나 컨테이너 환경 변수 및 실행 인수 등에 패스워드 등을 추가할 수 있지만 이미지 자체에 기밀 정보가 포함되어 있으면 도커 레지스트리에 기밀 정보도 업로드하게 되어 보안상 바람직하지 않음
        - 기밀 정보 내용을 변경하려면 이미지를 다시 빌드 해야함.
    - **파드나 디플로이먼트의 매니페스트를 통해 전달**
        - git 저장소와 같은 외부 서버에서 기밀 정보를 포함한 매니페스트를 관리하면 보안상 위험
        - 여러 애플리케이션에서 같은 기밀 정보를 사용할 경우 매니페스트 관리가 어려움
    - 사용자 이름이나 패스워드 등의 기밀 정보를 별도의 리소스에 정의하고 파드에서 읽어 들이는 시크릿 리소스 사용
    - 시크릿을 정의하고 있는 매니페스트는 base64로 인코드되어 있지만 암호화되어 있지 않아서 매니페스트 파일을 git 저장소에 업로드하는 것은 불가능. 이러한 문제를 해결하기 위해서 시크릿이 정의된 매니페스트를 암호화하는 `kubesec/SealedSecret/ExternalSecret` 같은 오픈 소스 소프트웨어를 사용

- **시크릿 분류**
    - 타입 목록
        - `Opaque`: 일반적인 범용 용도
        - `kubernetes.io/tls`: TLS 인증서용
        - `kubernetes.io/basic-auth`: 기본 인증용
        - `kubernetes.io/dockerconfigjson`: 도커 레지스트리 인증 정보용
        - `kubernetes.io/ssh-auth`: SSH 인증 정보용
        - `kubernetes.io/service-account-token`: 서비스 어카운트 토큰용
        - `bootstrap.kubernetes.io/token`: 부트스트랩 토큰용

- **일반적인 범용 용도의 시크릿**
    - **생성 방법**
        - 파일에서 값을 참조하여 생성: `--from-file`
        - envfile 에서 값을 참조하여 생성: `--from-env-file`
        - 직접 값을 전달하여 생성: `--from-literal`
        - 매니페스트에서 생성: `-f`
    - **파일로부터 생성**
        - 파일에 확장자를 붙이지 않는 것을 권장
        - 파일명이 키가 되므로 파일명에 확장자를 잘 붙이지 않음
        - 시크릿에 포함된 값을 내보내기
            - `echo -n "root" > ./username`
            - `echo -n "rootpassword" > ./password`
        - 파일을 가지고 시크릿을 생성
            - `kubectl create secret generic --save-config sample-db-auth --from-file=./username --from-file=./password`
        - data를 확인: base64 로 인코딩 돼서 조회
            - `kubectl get secrets`
            - `kubectl get secrets sample-db-auth -o json | jq .data`
        - 원문을 확인
            - `kubectl get secrets sample-db-auth -o json | jq -r '.data.username' | base64 -d`
            - `kubectl get secrets sample-db-auth -o json | jq -r '.data.password' | base64 -d`

    - **여러 개의 secret 을 하나의 파일로부터 읽고자 하는 경우에는 `envfile` 을 이용**
        - 파일을 생성(env-secret.txt)
            ```text
            username=root
            password=rootpassword
            ```
        - 시크릿 생성
            - `kubectl create secret generic --save-config sample-db-auth --from-env-file=./env-secret.txt`
        - 이미 있으면 secret을 지우고 함.
        - 확인
            - `kubectl get secrets sample-db-auth -o jsonpath='{.data.username}'`
        - 원문 확인
            - `kubectl get secrets sample-db-auth -o jsonpath='{.data.username}' | base64 -d`

    - 직접 입력해서 시크릿을 생성
        - `kubectl create secret generic --save-config sample-db-auth --from-literal=username=root`
    - 이미 있으면 삭제
        - `kubectl delete secret <시크릿이름>`
        - `kubectl delete secret sample-db-auth`
    - Base64 로 인코딩된 값을 매니페스트에 추가
        ```yaml
        apiVersion: v1
        kind: Secret
        metadata:
          name: sample-db-auth
        type: Opaque
        data:
          username: cm9vdA==
          password: cm9vdHBhc3N3b3Jk
        ```
    - 확인: `kubectl get secrets sample-db-auth -o jsonpath='{.data.username}' | base64 -d`
    - 생성할 때 data 대신에 `stringData` 를 사용하면 Base64 인코딩이 필요없음

        ```yaml
        apiVersion: v1
        kind: Secret
        metadata:
          name: sample-db-auth
        type: Opaque
        stringData:
          username: root
          password: rootpassword
        ```

- **TLS 인증서 타입 시크릿**
    - type에 `tls(Transport Layer Security - 전송 계층 보안)`
        - 쿠버네티스에서 HTTPS를 적용하거나 외부와 안전하게 통신하기 위해서 생성
        - 인그레스 리소스에서 HTTPS 통신을 위해서 많이 사용
        - example.com 에 TLS 를 적용
            - 인증서 파일을 생성(tls.crt, tls.key)
            - `kubectl create secret tls example-tls --cert=tls.crt --key=tls.key`
            - 인그레스 리소스에 적용
                ```yaml
                spec:
                  tls:
                  - hosts:
                    - example.com
                    secretName: example-tls
                ```
- **도커 레지스트리 타입 시크릿**
    - 도커 레지스트리가 Private 저장소인 경우 도커 이미지를 가져오려면 인증이 필요한데 이 인증 정보를 만들 때 시크릿으로 정의하여 사용할 수 있음
    - 실습
        - 레지스트리: `registry.example.com/myproject/myapp:1.0`
        - 시크릿 생성
            - `kubectl create secret docker-registry regcred --docker-server=registry.example.com docker-username=myuser dokcer-password=mypassword docker-email=user@example.com`
        - 워크로드 API

            ```yaml
            spec:
              containers:
              - name: app
                image: registry.example.com/myproject/myapp:1.0
              imagePullSecrets:
              - name: regcred
            ```

- **기본 인증 타입 시크릿**
    - 사이트에 접속할 때 로그인이 필요한 경우
    - 애플리케이션이 데이터베이스 같은 곳에 접속하고자 할 때 사용
    - `sample-basic-auth.yaml`

        ```yaml
        apiVersion: v1
        kind: Secret
        metadata:
          name: sample-basic-auth
        type: kubernetes.io/basic-auth
        data:
          username: 인코딩 값
          password: 인코딩 값
        ```

- **시크릿을 컨테이너에서 사용하는 패턴**
    - 환경 변수로 전달
        - 특정 키만 사용
        - 전체 키 사용
    - 볼륨으로 마운트
        - 특정 키만 사용
        - 전체 키 사용
    - 하나의 키를 환경 변수로 전달하는 샘플

        ```yaml
        apiVersion: v1
        kind: Pod
        metadata:
          name: sample-secret-single-env
          labels:
            app: sample-app
        spec:
          containers:
          - name: secret-container
            image: nginx:1.17
            env:
            - name: DB_USERNAME
              valueFrom:
                secretKeyRef:
                  name: sample-db-auth
                  key: username
        ```
        - 환경변수 확인: `kubectl exec -it sample-secret-single-env -- env | grep DB_USERNAME`
    - 시크릿 전체를 환경 변수로 전달하는 파드 샘플
        - 매니페스트(`sample-secret-multi-env.yaml`)
        ```yaml
        apiVersion: v1
        kind: Pod
        metadata:
          name: sample-secret-multi-env
          labels:
            app: sample-app
        spec:
          containers:
          - name: secret-container
            image: nginx:1.17
            envFrom:
            - secretRef:
                name: sample-db-auth
        ```
        - 배포: `kubectl apply -f sample-secret-multi-env.yaml`
        - 환경변수 확인: `kubectl exec -it sample-secret-multi-env -- env`

    - 볼륨으로 전달: 파일에 저장
        - 매니페스트(`sample-secret-multi-volume.yaml`)
        ```yaml
        apiVersion: v1
        kind: Pod
        metadata:
          name: sample-secret-multi-volume
          labels:
            app: sample-app
        spec:
          containers:
          - name: secret-container
            image: nginx:1.17
            volumeMounts:
            - name: config-volume
              mountPath: /config
          volumes:
          - name: config-volume
            secret:
              secretName: sample-db-auth
        ```
        - 기존 거 삭제: `kubectl delete pod sample-secret-multi-env`
        - 배포
        - 환경변수 확인: 
            - `kubectl exec -it sample-secret-multi-volume -- ls /config`
            - `kubectl exec -it sample-secret-multi-volume -- cat /config/username`

- **동적 시크릿 업데이트**
    - 볼륨 마운트를 사용한 시크릿에서는 일정 기간마다 `kube-apiserver` 로 변경을 확인하고 변경이 있을 경우 파일을 교체 
    - 기본 업데이트 주기는 60초인데 이 주기를 조정하고자 하는 kubelet 의 `sync-frequency` 옵션을 지정
    - 환경 변수를 사용한 경우는 파드를 기동할 때 환경 변수가 정해지기 떄문에 동적으로 변경할 수 없음

### 3) ConfigMap

- **개요**
    - 설정 정보 등을 Key-Value 로 저장할 수 있는 데이터 저장 리소스
    - 설정 파일 자체를 저장할 수 있음
    - 하나의 ConfigMap 에 저장할 수 있는 최대 용량은 1MB
    - 설정 파일 자체를 ConfigMap 에 저장해도 되고 특정 파라미터만 저장하는 것도 가능

- **ConfigMap 생성**
    - kubectl create 명령으로 생성하는데 `--from-file` 옵션으로 파일로부터 생성 가능하고 직접 입력한 문자열을 이용할 때는 `--from-literal` 옵션 지정이 가능
    - 파일로부터 만들면 파일 이름이 key 가 된다. 

    - nginx.conf 파일을 ConfigMap 으로 생성
        - `nginx.conf` 파일을 생성

            ```text
            user nginx;
            worker_processes auto;
            error_log /var/log/nginx/error.log warn;
            pid /var/run/nginx.pid
            ```
        
        - ConfigMap 생성: `kubectl create configmap --save-config sample-configmap --from-file=./nginx.conf`

        - 데이터 확인: 
            - `kubectl get configmaps sample-configmap -o json | jq .data`
            - `kubectl describe configmaps sample-configmap`
