
# GitHub Actions로 SSH 배포

## 1. 배포 흐름

`GitHub push` → 테스트 → Docker 이미지 빌드 및 Docker Hub 푸시 → SSH로 EC2 접속 → 새 컨테이너 실행

## 2. 사전 준비

- 배포 대상 EC2에 Docker를 설치한다.
- Docker Hub에 이미지 저장소를 생성한다.
- GitHub 저장소의 **Settings → Secrets and variables → Actions**에서 다음 Secrets를 등록한다.
    - `DOCKERHUB_TOKEN`: Docker Hub 액세스 토큰
    - `EC2_HOST`: EC2의 퍼블릭 IP 또는 도메인
    - `EC2_USERNAME`: EC2 로그인 사용자명(예: `ubuntu`)
    - `EC2_SSH_KEY`: EC2 접속용 PEM 개인 키 전체 내용
- 토큰과 개인 키는 코드나 노트에 직접 기록하지 않는다.

## 4. Docker 이미지 생성

`Dockerfile`

```dockerfile
FROM python:3.13-slim

WORKDIR /usr/src/app
COPY requirements.txt ./
RUN pip install --no-cache-dir -r requirements.txt
COPY . .

EXPOSE 5000
CMD ["python3", "-m", "flask", "run", "--host=0.0.0.0"]
```

로컬에서 이미지 빌드와 실행을 확인한다.

```bash
docker build -t <DOCKERHUB_USERNAME>/flaskweb:latest .
docker run -dit -p 5000:5000 --name flaskweb <DOCKERHUB_USERNAME>/flaskweb:latest
```

## 5. GitHub Actions CI/CD

`.github/workflows/ci-cd.yaml`

```yaml
name: CI/CD

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.13"
      - run: pip install -r requirements.txt
      - run: pytest

  build-and-push:
    needs: test
    # PR에서는 Secrets를 사용할 수 없으므로 이미지 푸시를 하지 않는다.
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Docker Hub 로그인
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}
      - name: 이미지 빌드 및 푸시
        uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ${{ secrets.DOCKERHUB_USERNAME }}/flaskweb:latest

  deploy:
    needs: build-and-push
    runs-on: ubuntu-latest
    steps:
      - name: EC2에 SSH로 배포
        uses: appleboy/ssh-action@v1.2.2
        with:
          host: ${{ secrets.EC2_HOST }}
          username: ${{ secrets.EC2_USERNAME }}
          key: ${{ secrets.EC2_SSH_KEY }}
          script: |
            docker pull ${{ secrets.DOCKERHUB_USERNAME }}/flaskweb:latest
            docker stop flaskweb 2>/dev/null || true
            docker rm flaskweb 2>/dev/null || true
            docker run -d --name flaskweb -p 5000:5000 --restart unless-stopped ${{ secrets.DOCKERHUB_USERNAME }}/flaskweb:latest
            docker image prune -f
```

`DOCKERHUB_USERNAME`도 GitHub Secret으로 등록한다. 배포 서버에서 비공개 이미지에 접근해야 한다면 해당 서버에도 Docker Hub 로그인을 별도로 설정한다.

```bash
sudo dd if=/dev/zero of=/swapfile bs=128M count=32
sudo chmod 600 /swapfile
sudo mkswap /swapfile

```

```bash
sudo docker run --detach \
  --hostname <GITLAB_HOST> \
  --publish 443:443 \
  --publish 80:80 \
  --publish 2222:22 \
  --name gitlab \
  --restart always \
  --volume /srv/gitlab/config:/etc/gitlab \
  --volume /srv/gitlab/logs:/var/log/gitlab \
  --volume /srv/gitlab/data:/var/opt/gitlab \
  --shm-size 256m \
  gitlab/gitlab-ce:latest
```

```bash
sudo docker logs -f gitlab
```

# ArgoCD

## 1. GitOps

### 1) 개요

- Git 저장소를 단일 소스로 사용하여 인프라를 코드로 제공하는 방법론 및 관행
- DevOps 문화가 이룩한 핵심 성과와 접근법을 실현하는 프레임워크를 제공
- GitOps 는 구현 방식에 열린 접근법으로 GitOps 프레임워크는 Git, 쿠버네티스 및 CI/CD 솔루션으로 구축할 수 있음

GitOps를 운영할 때의 핵심 원칙은 다음과 같다.

- Git을 신뢰할 수 있는 단일 소스(SSOT, Single Source of Truth)로 취급한다.
- 인프라와 애플리케이션의 원하는 상태를 코드와 매니페스트로 표현한다.
- 변경은 직접 운영 환경에서 수행하지 않고, Pull Request를 포함한 Git 워크플로우를 통해 검토·기록·반영한다.

### 2) GitOps 원칙

- 선언적 구성
    - GitOps 로 관리되는 시스템은 원하는 상태를 선언적으로 표현
    - 명령어 형태로 컨테이너 3개를 만들어라 라고 하는 것이 아니라 애플리케이션은 3개의 컨테이너를 사용하겠다고 선언하면 에이전트가 3이라는 숫자를 맞춰주는 방식

- 버전이 제어되는 불변의 저장소
    - 상태 관리에는 불변성 원칙과 버전 관리 방법론을 적용하며 버전 변경 이력은 완벽하게 유지되어야 한다.

- 자동 반영
    - 배포 환경에 설치된 소프트웨어 에이전트가 원하는 상태에 대한 선언적 표현을 Git 저장소에서 자동으로 끌어와야 함
    - 변경 사항이 버전 제어 시스템에 반영되면 어떠한 수동 작업도 수행하지 말아야 한다는 것
    - 지속적 조정

### 3) 사용하는 이유

- GitOps 는 개발자에게 익숙한 보편적 Git 기반 워크플로우를 사용해서 애플리케이션 개발부터 배포, 앱 수명 주기 관리 그리고 인프라 구성에 이르는 기존 프로세스를 확장
- 모든 변경 사항은 Git 저장소 기록을 통해 추적하고 감시하는데 이 접근법은 개발팀과 운영팀 모두에게 문제를 신속하게 추적하고 재현할 수 있어서 편리하고 보안이 전반적으로 개선됨
- 이점
    - 표준 워크플로우
    - 강화된 보안: 변경 사항을 미리 검토하고 예기치 않은 구성 변동을 감지하여 조치를 취함
    - 가시성 및 감사: Git 저장소의 변경 이력을 통해 클러스터의 모든 변경 사항을 캡쳐하고 추적
    - 멀티 클러스터 일관성: 많은 환경과 Kubernetes 클러스터에 대한 배포를 안정적이고 일관되게 구성


### 4) Kubernetes CI/CD

- 개요
    - 일반적인 CI/CD 파이프라인의 경우 CI 프로세스는 제출된 코드를 확인하고 CD 프로세스는 보안, IaC 또는 애플리케이션 프레임워크에 설정된 경계 등에 대한 요구 사항을 확인하고 적용
    - 모든 코드 변경 사항을 추적하므로 업데이트가 쉬워지고 롤백이 필요한 경우에 대비해 버전 관리 기능도 제공
    - CD 는 GitOps 의 도메인이며 CI 와 연동해서 다양한 환경에 앱을 배포
    - 쿠버네티스를 이용하면 클러스터 내부에 CI/CD 파이프라인을 쉽게 구현 가능
    - CI 소프트웨어는 애플리케이션을 나타내는 컨테이너 이미지를 생성해서 컨테이너 이미지 레지스트리에 저장
    - pull request 와 같은 Git 워크플로우를 통해 배포할 앱의 명세서 격인 매니페스트를 변경한 후 CD 동기화 루프를 개시

### ArgoCD

- namespace를 분리하는 방식
    - 별도의 namespace를 생성하고 애플리케이션을 구성하는데 필요한 모든 환경(ConfigMap, Secret, Ingress 등)을 추가해 나가는 방식
    - 이 방식은 시간이 지나면서 구성 드리프트가 발생하는데 개발 환경 클러스터 namespace 에만 최신 버전의 애플리케이션이 배포되거나 네트워크 정책 같은 리소스를 수정하게 되면 나머지 다른 환경을 개발 환경과 동일하게 맞추기 위해서 다른 부분을 확인해서 수동으로 변경을 해야하는데 이 부분을 단순화하기 위해서 kustomize 나 helm 같은 패키지 매니저를 사용
    - Helm 을 사용하면 여러 버전을 만들고 각 환경에 맞는 원하는 버전을 배포할 수 있지만 이력을 추적하기 어렵고 관리의 복잡성이 증가
- ArgoCD 는 선언적인 Kubernetes 의 GitOps 도구
- ArgoCD 안에 있는 애플리케이션 컨트롤러가 운영 중인 애플리케이션을 지속적으로 관찰하고 애플리케이션 상태와 원천 소스인 Git Repository 에 작성한 의도한 상태를 비교해서 변경 내용을 적용
- **사용 사례**
    - 배포 자동화: ArgoCD Controller 는 자동으로 클러스터를 Git Repository 에 의도한 상태로 푸시를 하게 되는데 Argo Event Framework 나 수동적인 요청을 통해서 가능
    - 관찰 가능성: ArgoCD 는 애플리케이션 상태가 깃 에서 의도한 상태와 동기화되어 있는지 식별할 수 있는 UI와 CLI 를 제공하고 ArgoCD Notification 엔진을 제공
    - 멀티 테넌시: 여러 클러스터를 관리하고 배포 가능

### 2) 도구

- ArgoCD: GitOps Tool
- Argo Rollouts: 점진적 배포 컨트롤러
- Argo Events
- Argo Workflows
    - 쿠버네티스 네이티브 워크플로우 엔진 & 오케스트레이션 도구
    - 복잡한 작업들을 DAG(Directed Acyclic Graph - 비순환그래프) 또는 Step 기반으로 정의하고 실행
    - 데이터 파이프라인, CI/CD 빌드 파이프라인, MLOps 워크플로우 등에서 많이 사용

### 3) 핵심 개념

- **조정**
    - Git Repository 에 담긴 의도한 상태를 현재 상태의 클러스터와 일치시켜야 하며 필요한 환경에 올바르게 전달을 해야함
    - Git Repository의 Helm 차트를 Kubernetes YAML로 렌더링한 뒤, 클러스터의 현재 상태와 비교한다. 이를 동기화 상태(sync status)라고 하며, 두 상태가 다르면 자동 또는 수동으로 `kubectl apply`를 실행해 적용한다.
    - Argo CD는 여러 템플릿 도구들을 지원하고 있는데 이런 도구들을 래퍼로 사용하는 것이 아니라 GitOps 원칙에 맞는 선언적 도구로 사용해서 원하는 상태를 배포하는데 목적을 두고 있음

- **핵심 구성 요소**
    - API Server
        - Web UI, CLI, Argo Event, CI/CD 시스템 같은 다른 시스템과 상호 작용을 위한 역할을 수행
        - 기능
            - 애플리케이션 관리 및 상태 보고
            - 애플리케이션 트리거 작업
            - Git Repository 와 Kubernetes 클러스터 관리
            - 인증
            - RBAC

    - Repository Server
        - 애플리케이션 Manifest 를 보관하는 git repository 로컬 캐시를 유지
    - Application Controller
        - 애플리케이션의 상태를 지속적으로 확인하고 의도한 상태와 비교
        - 사용자가 생성한 훅을 생명 주기 동안 실행
    - Argo Web UI, CLI 와 CI/CD 도구들이 Argo CD 의 API 서버와 직접 소통
        - Argo CD 는 Repository 를 확인해서 원하는 상태를 불러오고 기본적으로 3분마다 Git Repository 를 확인하기 때문에 즉시 반영되지 않으므로 지연을 피하기 위해서는 동기화 단계를 즉시 트리거할 수 있는 몇 가지 다른 옵션을 제공
        - Argo CD 에는 동기화 단계를 수동으로 시작할 수 있는 UI 를 포함
        - Argo CD 에는 API Server 와 상호작용 하기 위해 CLI 도 제공

### 4) Helm 을 이용한 Argo CD 설치

- helm repository 추가: `helm repo add argo https://argoproj.github.io/argo-helm`
- repository 업데이트: `helm repo update`
- argocd 를 설치할 namespace 생성: `kubectl create namespace argocd`
- 설치
    - `helm install argocd argo/argo-cd -n argocd [--version <차트버전>]`
    - `kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml`

    - 설치 확인: `kubectl get all -n argocd`
    - 서비스 확인: `kubectl get svc -n argocd`
        - argocd-server 의 서비스 타입을 확인
    - argocd-server 의 서비스 타입을 NodePort 로 변경해서 외부에서 접속할 수 있도록 해준다.
        - `kubectl patch svc argocd-server -n argocd -p '{"spec":{"type":"NodePort"}}'`
        - `kubectl edit services argocd-server -n argocd`
    - 서비스 확인: `kubectl get svc -n argocd`
        - argocd-server 의 서비스 타입을 확인하고 매핑된 NodePort 확인
        - 80:32358/TCP,443:32294/TCP
    - 초기 비밀번호 확인: `kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath="{.data.password}" | base64 -d`
        - 출력된 값으로 `admin` 계정에 로그인한 뒤 초기 비밀번호를 변경한다.
        - 접속 주소: `https://<KUBERNETES_MASTER_NODE_IP>:<HTTPS_NODE_PORT>`
    - 마스터 노드 IP와 `argocd-server` 서비스의 HTTPS NodePort를 조합해 브라우저에서 접속한다. 자체 서명 인증서를 사용한 경우 브라우저의 보안 경고가 표시될 수 있다.

### 5) Argo CD 를 이용

- 리소스 파일 생성

`application.yaml`

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: nginx-app
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://charts.bitnami.com/bitnami
    chart: nginx
    targetRevision: 22.6.5
    helm:
      parameters:
        - name: service.type
          value: NodePort
        - name: replicaCount
          value: "2"
  destination:
    server: https://kubernetes.default.svc
    namespace: nginx-deploy
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

- `repoURL`은 Helm 차트 저장소, `chart`는 배포할 차트, `targetRevision`은 사용할 차트 버전이다.
- `prune: true`는 Git에 없는 리소스를 삭제하고, `selfHeal: true`는 클러스터에서 발생한 구성 드리프트를 Git의 선언 상태로 되돌린다.
- `CreateNamespace=true`를 설정하면 대상 namespace가 없을 때 자동으로 생성한다.

배포 및 상태 확인 명령어는 다음과 같다.

```bash
kubectl apply -f application.yaml
kubectl get applications -n argocd
kubectl get all -n nginx-deploy
```
