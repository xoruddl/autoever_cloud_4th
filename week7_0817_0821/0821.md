# Docker

## 9. docker compose

### 4) 작성 방법

- 파일 이름: docker-compose.yaml, docker-compose.yml, compose.yaml, compose.yml 등

- **주 항목**
    - version (최신 Compose에서는 생략 가능)
    - services
    - networks
    - volumes
- **정의 내용**
    - image
    - networks
    - volumes
    - ports
    - environment
    - depends_on: 다른 서비스와의 의존 관계
    - restart: 컨테이너 종료 시 재시작 여부(no, always, on-failure, unless-stopped)

- **버전 정의**

    `version: "버전"`

    - 최신 Docker Compose에서는 `version` 항목이 더 이상 필수가 아니므로 생략할 수 있다.
    - 작성하는 경우에는 사용 중인 Docker Compose가 지원하는 형식을 확인해야 한다.

- **서비스 정의**
    - docker compose를 통해 실행할 서비스를 정의
    - 여러 개의 컨테이너를 묶어서 실행할 수 있으므로 복수형
    - services 하위에 실행될 컨테이너 서비스를 작성하고 하위 레벨에 docker run 명령과 유사하게 컨테이너 실행에 필요한 옵션을 작성

        ```yaml
        version: "3.8"
        services:
          myweb:
            image: nginx

          mydb:
            image: mariadb
        ```

    - 기본적으로 docker hub 에 있는 이미지를 이용
    - docker hub 에 없는 직접 개발한 애플리케이션의 경우 Dockerfile 사용이 가능
    - build 하위 항목에 Dockerfile 의 경로를 설정해주면 된다.
        - Dockerfile 의 경로가 현재 디렉토리가 아니면 context와 dockerfile 항목을 이용해서 세부 내용을 지정하는 것이 가능

        - 현재 디렉토리인 경우
            ```yml
            services:
              myweb:
                build: .
            ```
        - 현재 디렉토리가 아닌 경우
            ```yml
            services:
              myweb:
                build:
                  context: .
                  dockerfile: Dockerfile 경로
            ```
    - 하위 옵션
        - `container_name`: docker run의 `--name` 옵션과 동일하며 컨테이너 이름을 직접 지정함. 생략하면 일반적으로 `프로젝트명-서비스명-번호` 형식의 이름이 자동으로 부여됨
        - `ports`: docker run의 `-p` 옵션과 동일하며 호스트 포트와 컨테이너 포트를 연결함. 예를 들어 `8080:80`은 호스트의 8080번 포트를 컨테이너의 80번 포트에 연결함
        - `expose`: 컨테이너의 내부 포트를 문서화하며 호스트에는 공개하지 않음. 같은 네트워크의 컨테이너 간 통신에는 필수가 아님
        - `networks`: docker run의 `--network`(`--net`) 옵션과 관련된 설정으로, 최상위 레벨의 `networks`에 정의한 네트워크 이름을 지정함
        - `volumes`: docker run의 `-v`(`--volume`) 옵션과 동일하며 호스트 또는 named volume과 컨테이너의 디렉토리를 연결해 데이터를 컨테이너와 분리하고 지속적으로 보관함
        - `environment`: docker run의 `-e` 옵션과 동일하며 컨테이너 내부에서 사용할 환경 변수를 설정함. 환경 변수가 많으면 `env_file` 옵션에 환경 변수 파일 경로를 지정할 수 있음
        - `command`: docker run 이미지 이름 뒤에 작성하는 명령어와 유사하며, 이미지에 설정된 기본 실행 명령어를 덮어씀. 컨테이너가 시작될 때 실행됨

        - `restart`: docker run의 `--restart` 옵션과 동일하며 컨테이너의 재시작 정책을 지정함. `no`는 자동으로 재시작하지 않고, `always`는 컨테이너가 종료되면 항상 재시작하며, `on-failure`는 오류로 종료된 경우에만 재시작함. `unless-stopped`는 사용자가 직접 중지한 경우를 제외하고 재시작함
        - `depends_on`: 서비스 간의 종속성을 의미하며 지정한 서비스가 먼저 시작되도록 실행 순서를 정함. 단, 해당 서비스가 실제로 준비되거나 정상 동작할 때까지 기다리는 것은 아님

- **네트워크 정의**
    - 다중 컨테이너들이 사용할 최상위 네트워크 키를 정의하고 이하 하위 서비스 단위로 네트워크를 선택할 수 있음
    - networks 를 정의하지 않으면 자체 기본 네트워크를 자동으로 생성
    - 최상위 레벨에 networks를 정의하면 지정한 이름의 네트워크가 생성되고 대역은 별도로 지정하지 않는 한 Docker가 자동으로 할당함
    - 기존 네트워크를 사용하고자 하는 경우는 `external` 을 이용

        ```yml
        networks:
        default:
            external:
            name: 네트워크이름
        ```
- **볼륨 정의**

    - 데이터의 지속성을 유지하기 위해 최상위 레벨에 볼륨을 정의하고 서비스 레벨에서 볼륨명과 서비스 내부의 디렉토리를 바인드
    - 볼륨을 생성하면 docker 가 관리하는 가상 영역(/var/lib/docker/volume)에 자동 배치

### 5) docker run 과 docker compose 의 비교: 데이터베이스는 mysql:8.0 을 이용하고 wordpress:5.7 이미지를 이용한 웹 애플리케이션 서비스

- **docker 명령어**
    - 볼륨 생성
        - `docker volume create mydb_data`
    - 네트워크 생성
        - `docker network create myapp_net`
    - 컨테이너 생성
        ```bash
        docker run -dit --name mysql_app \
            -v mydb_data:/var/lib/mysql \
            --restart=always \
            -p 3306:3306 \
            --net=myapp_net \
            -e MYSQL_DATABASE=adam \
            -e MYSQL_USER=adam \
            -e MYSQL_PASSWORD=1234 \
            -e MYSQL_ROOT_PASSWORD=1234 \
            mysql:8.0
        ```
        ```bash
        docker run --name wordpress_app \
            -v myweb_data:/var/www/html \
            -v ${PWD}/myweb-log:/var/log \
            --restart=always \
            -p 8888:80 \
            --net=myapp_net \
            -e WORDPRESS_DB_HOST=mysql_app:3306 \
            -e WORDPRESS_DB_NAME=adam \
            -e WORDPRESS_DB_USER=adam \
            -e WORDPRESS_DB_PASSWORD=1234 \
            --link mysql_app:mysql \
            wordpress:5.7
        ```

- **docker compose 이용**
    - docker-compose.yaml 파일 작성

        ```yaml
        version: "3.9"

        services:
        mydb:
            image: mysql:8.0
            container_name: mysql_app
            volumes:
            - mydb_data:/var/lib/mysql
            restart: always
            ports:
            - "3306:3306"
            networks:
            - backend-net
            environment:
            MYSQL_DATABASE: adam
            MYSQL_USER: adam
            MYSQL_PASSWORD: 1234
            MYSQL_ROOT_PASSWORD: 1234

        myweb:
            depends_on:
            - mydb # mydb 먼저 생성
            image: wordpress:5.7
            container_name: wordpress_app
            ports:
            - "8000:80"
            networks:
            - backend-net
            - frontend-net
            volumes:
            - myweb_data:/var/www/html
            - ${PWD}/myweb-log:/var/log
            restart: always
            environment:
            WORDPRESS_DB_HOST: mydb:3306
            WORDPRESS_DB_USER: adam
            WORDPRESS_DB_PASSWORD: 1234
            WORDPRESS_DB_NAME: adam

        networks:
        frontend-net: {}
        backend-net: {}

        volumes:
        mydb_data: {}
        myweb_data: {}
        ```
    - 실행 : `docker compose up -d`

### 6) 하나의 네트워크로 묶인 경우 통신 방법

- **별개의 컨테이너로 생성하는 경우**
    - redis 컨테이너를 생성
        - `docker run --name myredis -d -p 6379:6379 redis`
    - redis를 사용하는 python application 생성
        - 가상환경을 생성: `python3 -m venv ./myvenv`
        - 가상환경 활성화: `source myvenv/bin/activate`
        - 패키지 설치
            ```bash
            pip install flask
            pip install redis
            ```
        - 라이브러리의 의존성을 파일로 내보내기
            ```bash
            pip freeze > requirements.txt
            ```
        - app.py 파일을 생성하고 작성

            ```python
            import redis
            from flask import Flask

            app = Flask(__name__)

            def web_hit_cnt():
                with redis.StrictRedis(host="localhost", port=6379) as conn:
                    return conn.incr("hits")

            @app.route("/")
            def hello():
                cnt = web_hit_cnt()
                return "<h1>Web Access Count: {}".format(cnt)

            if __name__ == "__main__":
                app.run(host="0.0.0.0", port=9000, debug=True)
            ```

        - 실행: `python app.py`
        - Redis의 6379 포트가 호스트에서 이미 사용 중이면, 기존 Redis 서비스를 중지하거나 포트 매핑을 변경해야 함

- **파이썬 애플리케이션을 컨테이너로 실행하는 경우**
    - Dockerfile을 작성하고 이미지를 빌드: `docker build -t flaskapp .`
    - 컨테이너 실행: `docker run -dit -p 9000:9000 --name flaskapp flaskapp`
    - 이 상태에서 Flask 컨테이너의 `localhost` 또는 `127.0.0.1`은 Redis 컨테이너가 아니라 Flask 컨테이너 자신을 의미하므로 Redis 연결 오류가 발생함
    - 별도 컨테이너끼리 통신하려면 Redis 컨테이너의 IP를 확인해 애플리케이션 접속 주소를 변경해야 함
        - `docker inspect myredis`


- **docker compose 활용**
    - docker-compose.yaml 파일 생성

```yaml
version: "3.9"
services:
  redis:
    image: redis:latest
    ports:
      - 6379:6379
    restart: always

  flask:
    build: .
    ports:
      - 9000:9000
    depends_on:
      - redis
    restart: always
```

    - `app.py`에서 Redis 접속 호스트를 서비스 이름으로 변경

        ```python
        def web_hit_cnt():
            with redis.StrictRedis(host="redis", port=6379) as conn:
                return conn.incr("hits")
        ```

    - 실행: `docker compose up -d`
    - Compose로 묶인 서비스는 동일한 기본 네트워크에서 서비스 이름(`redis`)으로 서로 통신할 수 있음
    - Dockerfile만 사용하는 경우 이미지 빌드와 컨테이너 실행을 따로 수행하지만, Compose의 `up`은 필요한 이미지 빌드와 서비스 실행을 한 번에 수행할 수 있음


### 7) docker-compose 명령

- build: Dockerfile 빌드
- config: 구성 파일의 내용 확인
- create: 서비스 생성
- down: 자원을 일괄 정지 후 삭제
- events: 실시간으로 이벤트 정보를 수신
- exec: 컨테이너에 명령 실행
- images: 이미지 정보
- kill: 컨테이너 강제 정지
- logs: 컨테이너의 실행 로그 정보 출력
- pause: 일시 정지
- port: 포트 출력
- ps: 현재 실행 중인 서비스 출력

- pull: 서비스 이미지 내려받기
- push: 서비스 이미지 레지스트리에 올리기
- restart: 서비스 재시작
- rm: 중지된 서비스 컨테이너 삭제
- run: 일회성 명령을 실행할 컨테이너 생성 및 실행
- scale: 서비스 컨테이너 수 설정
- start / stop: 서비스 시작 / 중지
- top: 실행 중인 프로세스 출력
- unpause: 일시 정지 해제
- up: 서비스 생성 및 시작
- version: 버전 정보 출력

- **스케일 조정**
    - docker-compose 파일 작성

        ```yaml
        version: "3.9"

        services:
          server_web:
            image: httpd:2
          server_db:
            image: redis
        ```

    - 실행 및 확인
        - `docker compose up -d`
        - `docker compose ps`
    - 스케일 설정: `docker compose up --scale server_db=3 --scale server_web=3 -d`
    - 종료: `docker compose down`

- **서비스 및 자원 삭제**
    - 기본 형식: `docker compose [-f 파일경로] down [옵션]`
    - 주요 옵션
        - `--rmi all`: 모든 서비스 이미지를 함께 삭제
        - `--rmi local`: 커스텀 태그가 없는 이미지만 삭제
        - `-v`: named volume 삭제
        - `--remove-orphans`: Compose 파일에 정의되지 않은 서비스 컨테이너도 삭제

### 8) Load Balancer

- **개요**
    - 서버에 가해지는 부하를 분산해주는 장치 또는 기술
    - 클라이언트와 서버 풀(server pool) 사이에 위치하며 한 대의 서버로 부하가 집중되지 않도록 트래픽을 관리해서 각각의 서버가 최적의 퍼포먼스를 보일 수 있도록 해주는 기술
    - 리소스 활용도를 최적화하고 처리량을 최대화하면 지연 시간을 줄이고 내결함성 구성을 보장하기 떄문에 안정적인 시스템 운영에 도움이 됨
    - docker 는 HaProxy, Nginx/Apache Load Balancer 등 외부 서비스와 컨테이너를 결합한 Load Balancing 구현이 가능

- **LoadBalancing 알고리즘**
    - `Round Robin`: 클라이언트의 요청을 번갈아가면서 순서대로 처리하는 알고리즘인데 서버 가중치 설정이 가능
    - `Least Connections`: 현재 연결된 클라이언트 수가 가장 적은 서버로 요청 전달
    - IP Hash: 해시키를 이용해서 IP별 INDEX를 설정해서 동일한 IP는 동일 서버로 경로를 보장하는 알고리즘, 해당 서버 장애 시 주소가 변경되고 균등 배분 보장 안됨
    - `General Hash`: 사용자가 정의한 키(Port, URI 문자열 등)를 이용해서 서버를 지정

    - `Least Time`: 요청에 대한 낮은 지연시간을 이용
        - header: 서버의 첫번째 바이트를 받는 시간 기준
        - last_byte: 서버에서 전체 응답을 받는 시간 기준
        - last_byte_inflight: 실패한 요청을 고려한 응답을 받는 시간 기준
    - `Random`
- **nginx Load Balancing 관련 파라미터**
    - `weight`: 가중치로 기본값은 1
    - `max_connes`, `queue`: 최대 클라이언트 연결 수 지정과 대기열 생성
    - `max_fails`: 최대 실패 횟수를 지정하는 것으로 설정한 횟수 이상 실패하면 서버를 분배 대상에게 제외
    - `backup`: 평소에는 동작하지 않고 모든 서버가 동작하지 않을 때 사용
    - `down`: down 키워드가 있는 서버는 사용하지 않지만 ip_hash 인 경우 사용

- **nginx를 이용해서 컨테이너 로드밸런싱을 구축**
    - 디렉토리 생성
        - `mkdir alb && cd alb`
        - `mkdir nginx_alb pyfla_app1 pyfla_app2 pyfla_app3`

    - nginx 설정
        - 디렉토리 이동: `cd nginx_alb`
        - Dockerfile 작성

            ```dockerfile
            FROM nginx
            RUN rm /etc/nginx/conf.d/default.conf
            COPY nginx.conf /etc/nginx/conf.d/default.conf
            ```
        - nginx.conf 파일 작성

            ```conf
            upstream web-alb{
                server 172.17.0.1:5001;
                server 172.17.0.1:5002;
                server 172.17.0.1:5003;
            }

            server{
                listen 80;
                location /{
                    proxy_pass http://web-alb
                }
            }
            ```
    - python 애플리케이션 작성
        - `cd ../pyfla_app1`
        - pyfla_app.py 파일을 생성하고 작성

            ```python
            from flask import Flask

            app = Flask(__name__)

            @app.route("/")
            def index():
                return "Web Application 1\n"

            if __name__ == "__main__":
                app.run(debug=True, host="0.0.0.0")
            ```

        - Dockerfile 작성

            ```dockerfile
            FROM python:3
            WORKDIR /
            COPY . .
            RUN pip install flask
            ENTRYPOINT ["python3"]
            CMD ["pyfla_app.py"]
            ```

        - 두 파일을 `pyfla_app2`, `pyfla_app3` 디렉터리에 복사하고, 각 `pyfla_app.py`의 응답 문자열을 `Web Application 2`, `Web Application 3`으로 수정
    - `alb` 디렉터리에서 Compose 파일 작성

        ```yaml
        version: "3.9"

        services:
          pyfla_app1:
            build: ./pyfla_app1
            ports:
              - "5001:5000"
          pyfla_app2:
            build: ./pyfla_app2
            ports:
              - "5002:5000"
          pyfla_app3:
            build: ./pyfla_app3
            ports:
              - "5003:5000"
          nginx:
            build: ./nginx_alb
            ports:
              - "8000:80"
            depends_on:
              - pyfla_app1
              - pyfla_app2
              - pyfla_app3
        ```

    - 실행: `docker compose up --build -d`
    - 가중치 변경 예: `server 172.17.0.1:5001 weight=3;`으로 설정하면 첫 번째 서버에 상대적으로 더 많은 요청을 전달함


### 9) 환경 변수 삽입 및 관리

- 환경 변수를 다루는 방법
    - compose 파일에 직접 입력
    - 쉘 환경 변수에 등록
    - 환경 변수 파일로 구성
    - Dockerfile 에 환경 변수를 직접 삽입

- **Compose 파일에 직접 입력**

    ```yaml
    services:
      mysql:
        image: mysql:8
        restart: unless-stopped
        ports:
          - "3306:3306"
        environment:
          MYSQL_ROOT_PASSWORD: password
    ```

    - 비밀번호를 Compose 파일에 직접 작성하면 Git 등의 저장소에 올릴 때 노출될 수 있음

- **쉘 환경 변수 이용**
    - 환경 변수 생성: `export MYSQL_ROOT_PASSWORD=password`
    - Compose 파일에서는 `${변수명}` 형식으로 참조

        ```yaml
        environment:
          MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD}
        ```

    - 민감한 정보를 더 안전하게 관리해야 하면 HashiCorp Vault와 같은 별도 비밀 관리 솔루션을 사용할 수 있음

## 10. Docker Swarm

### 1) 개요

- 여러 도커 호스트를 클러스터로 묶어주는 오케스트레이션 도구

- 컨테이너 오케스트레이션 도구 없이는 도커 호스트 여러 대를 사용하는 확장성 있는 애플리케이션을 만들기가 어려움
- 어느 도커 호스트에 어떤 컨테이너를 배치해야 하는지 서로 다른 호스트에 위치한 컨테이너 간의 통신은 어떻게 제어해야 할 지를 조율하는 것은 쉽지 않은 일
- **용어**
    - `docker-compose`: 여러 컨테이너로 구성된 도커 애플리케이션을 관리하는 것으로 주로 단일 호스트
    - `docker swarm`: 클러스터 구축 및 관리로 멀티 호스트에서 사용
    - `docker service`: 스웜에서 클러스터 안의 서비스
    - `docker stack`: 스웜에서 여러 개의 서비스를 합한 전체 애플리케이션

- **주요 기능**
    - **역할이 분리된 분산 설계**
        - 역할 종류
            - `manager node`
            - `leader node`
            - `worker node`
        - 단일 관리자 환경이라면 manager node와 workder node 로 분리해서 manager node 가 전문적 관리를 수행하고 worker node 가 도커 호스트의 역할을 수행
        - manager node 가 여러 개라면 manager node 는 중 하나를 리더 매니저 노드로 구성해서 관리
        - manager node 가 클러스터의 관리 역할을 수행하는데 컨테이너 스케쥴링 및 상태 유지 등을 제공하고 작업자 노드는 컨테이너를 실행하는 역할만 수행

        - 쿠버네티스와 비교해보면 쿠버네티스의 매니저 노드인 마스터 노드는 컨테이너 서비스를 제공하지 않지만 도커 스웜의 매니저 노드는 작업자 노드의 역할을 수행할 수 있음
        - 관리 역할을 수행하는 노드의 부하를 고려해서 각 역할은 분리해서 사용하기를 권장하는데 서비스를 생성 시 `--constraint node_role!=manager` 옵션을 사용하면 manager 노드에서는 서비스 컨테이너를 수행하지 않도록 한다.
    - 도커 엔진과 통합된 다중 서버 클러스터 환경 구성: 별도의 오케스트레이션 도구를 설치할 필요가 없음
    - **서비스 확장과 원하는 상태 조정**
        - Replicas Option 을 이용해서 중복된 서비스 배포 가능
        - 초기 구성 후 스웜 관리자를 이용해서 애플리케이션의 가용성에 영향을 주지 않고 서비스 확장 및 축소를 수행할 수 있음
        - 배포된 서비스는 매니저 노드를 통해서 지속적으로 모니터링
        - 사용자가 요청한 상태와 다르게 서비스 장애가 생길 경우 장애가 발생한 서비스를 대체할 새로운 복제본을 자동으로 생성해서 사용자 요구를 지속하게 되는데 이것이 요구 상태 관리(desire state management)
        - 대부분의 오케스트레이션 도구의 목적이 요구 상태 관리
    - **서비스 스케쥴링**
        - 서비스 컨테이너를 배포하는 작업
        - 노드 선택 전략은 swarm manage --strategy 옵션 을 이용해서 설정
            - `spread`: 모든 작업자 노드에게 균등하게 분산
            - `binpack`: 작업자 노드의 자원 사용량을 고려하여 할당하는 자원 대비 전략
            - `random`: 무작위
        - 도커 스웜 모드는 단일 옵션으로 고가용성 분산 알고리즘을 사용하는데 생성되는 서비스의 복제본을 분산 배포하기 위해서 현재 복제본이 가장 적은 작업 노드 중에서 이미 스케쥴링된 다른 서비스 컨테이너 수가 가장 작은 작업자 노드를 우선 선택
    - **로드 밸런싱**
        - 도커 스웜 모드를 초기화 하면 자동으로 생성되는 네트워크 드라이버 중 하나가 `Ingress Network`
        - Ingress Network 는 서비스의 노드 간 load balancing 과 외부에 서비스를 노출하기 위한 overlay network
        - 도커 스웜 모드는 서비스 컨테이너에 publishedport 를 자동으로 할당(30000 ~ 32767) 하거나 수동 노출할 포트를 구성할 수 있고 서비스 컨테이너가 포트를 오픈하면 동시에 모든 노드에 있는 동일한 포트가 오픈되고 이로 인해서 클러스터에 합류되어 있는 어떤 노드에 요청을 전달해도 실행 중인 서비스 컨테이너에 자동 전달되는데 모든 노드가 스웜 모드의 routing mesh 에 참여하기 때문
        - worker node 1과 worker node 2 두 개의 워커 노드가 있고 컨테이너를 복제하지 않고 1개만 배포해 worker node 1에 배치된 경우에도, worker node 2로 요청을 보내면 routing mesh를 통해 실행 중인 서비스 컨테이너로 자동 전달됨
    - **서비스 검색**
        - 도커 스웜 모드에서는 서비스 검색을 위해 자체 DNS 서버를 통한 서비스 검색 기능을 제공
        - 스웜 매니저 노드는 클러스터의 서비스에 고유 DNS 이름을 부여하며, 내장 DNS 서버가 이를 해석함. 이를 service discovery라고 함
    - **Rolling Update**
        - 도커 스웜은 현재 실행 중인 서비스 컨테이너를 업데이트 하는 경우 노드 단위로 점진적으로 적용할 수 있는 Rolling Update를 제공
        - 업데이트를 하는 경우 새로운 서비스 컨테이너를 먼저 생성해서 헬스 체크를 하고 서비스가 정상적으로 구동이 되면 이전 서비스 컨테이너를 삭제하는 방식으로 동작하는 업데이트
        - 기본적으로 하나를 먼저 만들고 하나를 삭제하는 구조지만 여러 개를 한꺼번에 만들 수도 있고 삭제를 먼저 할 수도 있다.
        - 업데이트를 실패하면 자동적으로 이전 정상적인 상태로 롤백이 된다.
- **쿠버네티스와의 차이**
    - 기능이 간단한 컨테이너 오케스트레이션 도구로 설계
    - 네트워크와 서비스의 개념을 도커 컴포즈에서 차용해 오케스트레이션 도구로써 도커 엔진에 안정적으로 동작
    - 쿠버네티스는 주요 클라우드 서비스에서 매니저드 서비스 형태로 많이 제공
    - 쿠버네티스는 확장성이 뛰어나서 클라우드 사업자가 로드밸런서, 스토리지 등과 같은 애플리케이션 배포를 지원하는 자사 프로덕트와 통합하기에 유리
    - 현재까지 도커 스웜을 매니지드 서비스로 제공하는 클라우드 업체는 없음
    - 클라우드 환경에서 도커 스웜을 사용하고자 하면 클러스터를 직접 구축해야 함
    - 쿠버네티스보다 쉽다.

- **선택 기준**
    - Infra structure
        - 클라우드 환경이면 쿠버네티스
    - 학습 곡선
        - 도커만 학습한 경우는 도커 스웜
    - 기능
        - 쿠버네티스가 기능이 훨씬 다양
