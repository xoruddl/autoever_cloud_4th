### 4) Docker Swarm에서의 볼륨

- 볼륨은 컨테이너 외부에 데이터를 영속적으로 저장하기 위한 개념입니다.

- **사용 방식**

  - **Named Volume(기본)**
    - 별도 설정 없이 각 노드의 로컬 디스크에 생성됩니다.
    - 컨테이너가 다른 노드에 재스케줄링되면 이전 노드의 데이터를 읽을 수 없습니다.

  - **Node Placement**
    - `placement.constraints`로 컨테이너를 특정 노드에 고정하여, 해당 노드의 로컬 디스크를 사용합니다.
    - 단일 데이터베이스나 상태 저장 애플리케이션에 사용할 수 있습니다.

  - **NFS/네트워크 스토리지**
    - 네트워크 스토리지를 사용해 클러스터 전체가 공유하는 볼륨을 구성합니다.
    - 직접 구축한 NFS 서버나 퍼블릭 클라우드의 스토리지 서비스를 사용할 수 있습니다.

# Kubernetes

## 1. Kubernetes

### 1) Container Runtime

- **개요**
  - 일반적인 가상화 소프트웨어는 하드웨어 수준에서 가상화하지만, 컨테이너 가상화는 운영체제 수준에서 가상화합니다.
  - 컨테이너는 운영체제 커널을 공유하므로 상대적으로 가볍고 유연합니다.
  - 가상 머신보다 적은 자원을 사용하여 하나의 시스템에서 더 많은 애플리케이션을 실행할 수 있습니다.
  - 런타임은 프로그램이 실행되는 환경을 뜻합니다. 예를 들어 JavaScript가 브라우저에서 실행될 때 브라우저가 런타임입니다.
  - 컨테이너를 생성하고 실행할 수 있게 해 주는 소프트웨어를 **Container Runtime**이라고 합니다.

- **종류**

  - **containerd**
    - 컨테이너 실행을 관리하는 오픈 소스 런타임입니다.
    - Docker 및 Kubernetes 같은 컨테이너 오케스트레이션 시스템에서 컨테이너 실행을 처리하는 데 사용됩니다.
    - 이미지 다운로드와 압축 해제부터 컨테이너 실행·감독까지 전체 수명 주기를 관리합니다.

  - **Docker**
    - containerd를 기반으로 동작하는 데몬입니다.
    - 컨테이너를 생성하고 관리하는 데 필요한 기능을 제공합니다.
    - Docker는 컨테이너의 빌드·배포·실행을 관리하며, 내부적으로 containerd를 사용합니다.

  - **CRI-O**
    - Red Hat, Intel, SUSE, IBM 등의 커뮤니티를 중심으로 개발된 오픈 소스 런타임입니다.
    - Kubernetes의 CRI(Container Runtime Interface)를 구현하여 Docker 대안으로 사용할 수 있습니다.

### 2) Container Orchestration

- **개요**
  - 다수의 컨테이너를 연결·실행하고 상태를 추적·보존하여 안정적으로 운영하게 해 주는 솔루션입니다.
  - 여러 시스템에 컨테이너를 분산 배치하거나, 장애가 난 컨테이너를 교체하는 역할을 합니다.

- **종류**

  - **Docker Swarm**
    - 설치와 사용이 간단하여 소규모 환경에 유용합니다.
    - 대규모 환경에 적용하려면 추가적인 구성과 운영 설계가 필요합니다.

  - **Mesos**
    - Apache 오픈 소스 프로젝트로, Twitter·Airbnb·Apple·Uber 등에서 사용된 사례가 있습니다.
    - 기능을 충분히 활용하려면 분산 관리 시스템 등 여러 솔루션과의 연동이 필요합니다.

  - **Nomad**
    - HashiCorp의 오케스트레이션 도구로 간단한 구성으로 환경을 제공하는 것이 특징입니다.
    - Consul(서비스 검색·구성·분할) 및 Vault(암호화 저장소)와 연동하기 좋습니다.

  - **Kubernetes**
    - Google의 Borg 시스템에서 발전했으며, 현재 CNCF에서 관리합니다.

### 3) Kubernetes 개요

- `k8s`라고도 부르는데, `k`와 `s` 사이에 8개의 글자가 있기 때문입니다.
- Kubernetes의 이점을 얻으려면 애플리케이션을 Kubernetes에 배포한다는 전제 아래 설계해야 합니다.
- 여러 대의 물리 서버가 존재하는 환경을 전제하며, 각 서버에서 여러 컨테이너를 실행합니다.
- Docker Compose 파일과 유사한 정의 파일을 작성하면, Kubernetes가 여러 서버에 컨테이너를 생성하고 관리합니다.

#### Kubernetes를 사용하는 이유

- **자동화된 컨테이너 오케스트레이션**
- **무중단 서비스**
- **효율적인 자원 사용**
  - 컨테이너별 리소스 설정이 가능하며, Service와 Ingress가 트래픽 라우팅을 담당합니다.
- **유연한 확장성**
  - 오토스케일링을 지원합니다.
- **원하는 상태 유지(Desired State)**
  - YAML 파일로 원하는 상태를 정의하면, Kubernetes가 컨테이너를 생성·삭제하며 그 상태를 유지합니다.
- **Self Healing(자가 치유)**
  - 컨테이너에 장애가 발생하면 자동으로 재시작합니다.
  - 노드에 장애가 발생하면 해당 노드의 애플리케이션을 다른 노드로 이동시킵니다.
- **클라우드 벤더 종속성 완화**
  - 주요 퍼블릭 클라우드가 Kubernetes를 지원합니다.

### 4) Kubernetes 리소스

- **Workload API**: 컨테이너 실행과 관련된 리소스
  - Pod, ReplicationController, ReplicaSet, Deployment, DaemonSet, StatefulSet, Job, CronJob

- **Service API**: 컨테이너를 외부에 공개하는 엔드포인트를 제공하는 리소스
  - ClusterIP, ExternalIP, NodePort, LoadBalancer, Headless, ExternalName, Ingress

- **Config & Storage API**: 설정·기밀 정보·영구 볼륨과 관련된 리소스
  - Secret, ConfigMap, PersistentVolumeClaim

- **Cluster API**: 보안·쿼터와 관련된 리소스
  - Node, Namespace, PersistentVolume, ResourceQuota, ServiceAccount, Role, ClusterRole, RoleBinding, ClusterRoleBinding, NetworkPolicy

- **Metadata API**: 클러스터 내부의 다른 리소스를 관리하는 리소스
  - LimitRange, HorizontalPodAutoscaler, PodDisruptionBudget, CustomResourceDefinition

### 5) Kubernetes 아키텍처

#### Pod

- Pod는 Kubernetes에서 생성할 수 있는 가장 작은 배포 단위이며, 하나 이상의 컨테이너를 포함합니다.
- Pod, Service, Volume, Namespace 등을 묶어 Kubernetes에서 상태 관리가 필요한 대상을 **객체(Object)**라고 합니다.
- Kubernetes는 컨테이너를 개별적으로 배포하지 않고, 유사한 역할을 수행하는 컨테이너를 Pod 단위로 묶어 배포합니다.
- 예를 들어 웹 애플리케이션과 데이터베이스는 서로 연관되어 있지만 역할이 다르므로, 일반적으로 별도 컨테이너로 실행합니다.

#### Kubernetes 구조

- **Cluster**
  - 여러 리소스를 관리하는 집합체입니다.
  - Control Plane(Master Node)과 Worker Node로 구성됩니다.

- **Node**
  - 컨테이너가 배치되는 대상입니다.
  - Kubernetes 클러스터에는 하나 이상의 Control Plane 노드가 필요합니다.

- **Control Plane(Master Node)**
  - Kubernetes 클러스터 전체를 관리합니다.
  - `kubectl`을 사용하여 초기 설정과 운영 조정을 수행할 수 있습니다.

- **Persistent Storage**
  - Pod는 휘발성이므로 삭제되면 내부 데이터도 함께 사라집니다.
  - 중요한 데이터는 Pod 외부의 영구 스토리지에 저장해야 하며, CSI(Container Storage Interface)로 외부 스토리지를 Pod에 연결할 수 있습니다.

- **Worker Node**
  - Container Runtime이 설치된 환경이며, Pod가 실제로 생성·유지되는 노드입니다.

### 6) Kubernetes 클러스터 구축

#### 구축 방법

- **Local Kubernetes**: 물리 머신 한 대에 구축합니다.
- **구성형 Kubernetes**: 온프레미스나 클라우드 환경의 여러 컴퓨터에 클러스터 구축 도구를 사용합니다.
- **관리형 Kubernetes**: 퍼블릭 클라우드가 제공하는 관리형 서비스를 사용합니다.

#### Local Kubernetes

- **Docker Desktop**: 로컬 Kubernetes를 활성화해 사용할 수 있습니다.
- **Minikube**
  - 쉽게 설치하여 사용할 수 있습니다.
  - Docker, VirtualBox, 베어메탈 등의 드라이버 또는 하이퍼바이저가 필요합니다.
  - <https://minikube.sigs.k8s.io/docs/start/>
- **kind**
  - Kubernetes 자체 테스트를 위해 만들어졌으며, 로컬 개발과 CI에도 사용할 수 있습니다.
  - <https://kind.sigs.k8s.io/docs/user/quick-start>
- **k3s / k0s**
  - 설치가 쉬운 경량 Kubernetes 클러스터 구축 도구입니다.
  - k3s: <https://docs.k3s.io>
  - k0s: <https://docs.k0sproject.io/head/install/>

#### 구성형 Kubernetes

- Kubernetes 클러스터를 자동으로 구성하는 솔루션을 이용합니다.
- `kubeadm`, `kops`, KRIB, Kubespray 등이 있으며, `kubeadm`을 많이 사용합니다.

#### kubeadm으로 클러스터 구축

##### 사전 준비

- 서로 통신할 수 있는 머신을 준비합니다.
- Control Plane 노드는 CPU 코어가 2개 이상이어야 합니다. 코어가 하나이면 클러스터 초기화 과정에서 오류가 발생할 수 있습니다.
- 호스트 이름 변경: `sudo hostnamectl set-hostname <이름>`
- 고정 IP 설정: `/etc/netplan` 디렉터리에 YAML 파일을 작성하여 설정합니다.

##### 기본 설정

- 패키지 업데이트

  ```bash
  sudo apt update && sudo apt upgrade -y
  ```

- 필요한 패키지 설치

  ```bash
  sudo apt install -y curl apt-transport-https ca-certificates software-properties-common gnupg
  ```

- Swap 비활성화
  - 가상 메모리 사용으로 인한 문제를 방지합니다.

  ```bash
  sudo swapoff -a
  sudo sed -i '/ swap / s/^\\(.*\\)$/#\\1/g' /etc/fstab
  ```

- 커널 모듈과 `sysctl` 설정

  ```bash
  cat <<EOF | sudo tee /etc/modules-load.d/k8s.conf
  overlay
  br_netfilter
  EOF

  sudo modprobe overlay
  sudo modprobe br_netfilter

  cat <<EOF | sudo tee /etc/sysctl.d/k8s.conf
  net.bridge.bridge-nf-call-iptables  = 1
  net.ipv4.ip_forward                 = 1
  net.bridge.bridge-nf-call-ip6tables = 1
  EOF

  sudo sysctl --system
  ```

##### Container Runtime 설치

```bash
sudo apt install -y containerd
sudo mkdir -p /etc/containerd
containerd config default | sudo tee /etc/containerd/config.toml
```

##### containerd 설정

```bash
sudo sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml
sudo systemctl restart containerd
sudo systemctl enable containerd
```

##### Kubernetes 설치

```bash
sudo curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.30/deb/Release.key | \\
  sudo gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg

echo "deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.30/deb/ /" | \\
  sudo tee /etc/apt/sources.list.d/kubernetes.list

sudo apt update
sudo apt install -y kubelet kubeadm kubectl
sudo apt-mark hold kubelet kubeadm kubectl
```

##### 클러스터 구성

- **Control Plane 노드에서 작업**

  ```bash
  sudo kubeadm init --pod-network-cidr=10.244.0.0/16
  ```

  - 초기화에 성공하면 Worker Node를 연결하는 `kubeadm join` 명령이 출력됩니다.
  - CPU 2코어 이상, 메모리 2GB 이상을 준비합니다.

- Kubernetes 설정 파일 생성

  ```bash
  mkdir -p $HOME/.kube
  sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
  sudo chown $(id -u):$(id -g) $HOME/.kube/config
  ```

- Flannel CNI 설치

  ```bash
  kubectl apply -f https://raw.githubusercontent.com/coreos/flannel/master/Documentation/kube-flannel.yml
  ```

- **Worker Node에서 작업**
  - 초기화 결과로 출력된 명령을 그대로 사용하여 클러스터에 연결합니다.

  ```bash
  sudo kubeadm join <CONTROL_PLANE_IP>:6443 --token <TOKEN> \\
    --discovery-token-ca-cert-hash sha256:<HASH>
  ```

- Worker Node 연결 후 노드 상태 확인

  ```bash
  kubectl get nodes
  ```

##### 클러스터 삭제

> 아래 명령은 Kubernetes 관련 설정과 데이터를 삭제합니다. 대상 노드와 필요한 데이터를 확인한 후 실행합니다.

```bash
sudo kubeadm reset -f
sudo rm -rf /etc/kubernetes/*
sudo rm -rf /var/lib/kubelet/*
sudo rm -rf ~/.kube
sudo systemctl daemon-reload
sudo systemctl restart containerd
sudo systemctl restart kubelet
```

### 7) Kubernetes 컴포넌트

- Control Plane에는 `etcd`, API Server, Controller Manager, Scheduler 등이 있습니다.
- Worker Node에는 `kube-proxy`, `kubelet`, Container Runtime 등이 있습니다.

#### kubectl

- Kubernetes에 명령을 전달하는 CLI 도구입니다.
- 바이너리 형태로 배포되므로 반드시 Control Plane에 설치할 필요는 없습니다.
- API Server와 통신하므로 Control Plane에 구성하는 것이 일반적입니다.

#### API Server

- Kubernetes 클러스터의 API를 제공하는 프로세스입니다.
- 클러스터로 전달된 요청을 검증합니다.
- `kubectl` 명령은 API Server로 전달되며, API Server는 요청을 검증한 후 적절한 구성 요소가 처리하도록 합니다.

#### etcd

- 클러스터 리소스의 상태 정보를 저장하는 키-값 데이터베이스입니다.
- API Server는 원하는 상태를 `etcd`에 저장하며, 컨트롤러가 이를 바탕으로 실제 상태를 맞춥니다.

#### Scheduler

- Pod를 어느 Worker Node에 할당할지 결정합니다.
- Worker Node의 리소스 사용량, 레이블, 노드 상태 등을 참고합니다.

#### Controller Manager

- 클러스터의 실제 상태를 지속적으로 감시하고, 선언된 상태와 일치하도록 여러 컨트롤러를 실행합니다.
- 리소스를 모니터링하고 필요한 변경을 수행하며, 장애 시 복구 작업을 수행합니다.

#### kubelet

- 각 Worker Node에서 실행되는 에이전트입니다.
- API Server로부터 전달받은 Pod 정보를 바탕으로 컨테이너 실행을 관리합니다.
- Pod 상태를 API Server에 보고하고, 이 정보는 `etcd`에 저장됩니다.

#### kube-proxy

- Kubernetes 클러스터에서 네트워크 프록시 역할을 하며, Service와 Pod 사이의 트래픽을 라우팅합니다.
- 각 노드에서 Service 기능을 구현하고, 클러스터 내부 트래픽을 적절히 분배합니다.
- Service의 가상 IP로 들어온 트래픽이 실제 Pod에 전달되도록 설정합니다.
- `iptables`, `ipvs` 등의 방식으로 트래픽을 제어합니다.
- 일반적으로 모든 노드에서 DaemonSet 형태로 실행됩니다.

  ```bash
  kubectl get pods -n kube-system
  ```

#### Container Runtime 지원

- Kubernetes 1.20부터 Docker Engine의 내장 dockershim은 사용 중단(deprecated)되었고, 1.24에서 제거되었습니다.
- containerd와 CRI-O 같은 CRI 호환 런타임을 사용할 수 있습니다.

### 8) Kubernetes Controller

- Controller는 Pod의 원하는 상태를 유지하도록 관리합니다.

- **ReplicaSet**
  - 유지할 Pod 개수를 결정합니다.
  - ReplicaSet이 관리하는 동일한 구성의 Pod를 Replica라고 합니다.

- **Deployment**
  - Stateless 애플리케이션을 배포할 때 사용하는 기본 Controller입니다.
  - ReplicaSet의 상위 개념으로, 배포와 업데이트를 관리합니다.

- **DaemonSet**
  - 모든(또는 조건에 맞는) Node에 Pod를 배포하고 관리합니다.
  - 노드별 성능 수집, 로그 수집 등에 사용합니다.

- **StatefulSet**
  - 상태를 저장하는 애플리케이션에 사용하는 Controller입니다.
  - Pod 집합의 배포와 스케일링을 관리하며, Pod의 순서와 고유 식별자를 보장합니다.
  - 재스케줄링 이후에도 지속되는 식별자를 가집니다.

- **Job**
  - 하나 이상의 Pod가 지정된 횟수만큼 성공적으로 실행되도록 관리합니다.

- **CronJob**
  - 지정한 일정에 따라 Job을 실행합니다.

### 9) Kubernetes Service

#### 개요

- Pod는 클러스터 안에서 이동할 수 있습니다. Worker Node에 문제가 생기면 다른 Node에서 다시 생성될 수 있고, Pod IP도 바뀔 수 있습니다.
- 동적으로 변하는 Pod에 고정된 방식으로 접근하기 위해 Service를 사용합니다.
- Service를 사용하면 Pod가 클러스터 어디에 있든 고정된 주소로 접근할 수 있으며, 유형에 따라 클러스터 외부에 노출할 수도 있습니다.
- 하나의 Service는 일반적으로 동일한 구성을 가진 Pod 집합을 관리합니다.
- Service는 고정된 IP 주소를 제공하고 여러 Pod에 통신을 분배하는 로드 밸런싱 역할을 합니다.

#### Service 종류

- **ClusterIP**: 클러스터 내부에서 Pod끼리 통신할 때 사용합니다.
- **NodePort**: Worker Node의 IP와 포트를 이용해 서비스를 외부로 노출합니다.
- **LoadBalancer**: 외부 로드 밸런서와 연결하고, 외부 IP로 접근할 수 있게 합니다.
- **Ingress**: 호스트 이름, URI, 경로 등 HTTP/HTTPS 규칙에 따라 외부 요청을 Service로 라우팅합니다.
- **ExternalName**: 외부 FQDN에 대한 CNAME 매핑을 제공하여 Pod가 해당 도메인 이름으로 통신할 수 있게 합니다.

### 10) Kubernetes 네트워크

#### 네트워크 특징

- Pod 네트워크와 호스트(Node) 네트워크는 다릅니다.
  - Node는 물리 네트워크를, Node 내부의 Pod는 가상 네트워크를 사용합니다.
- 하나의 Pod에 두 개 이상의 컨테이너를 배치할 수 있습니다.
  - 같은 Pod의 컨테이너는 네트워크 네임스페이스와 IP를 공유합니다.
  - 컨테이너 간 포트 번호는 중복될 수 없으며, `localhost:<포트>`로 통신할 수 있습니다.
- Pod IP는 재생성·재배치에 따라 변경될 수 있으므로, 일반적인 서비스 간 통신에는 IP 대신 Service 이름을 사용합니다.

#### 다른 Node의 Pod와 통신

- 서로 다른 Node에 있는 Pod 간 통신에는 CNI(Container Network Interface) 플러그인이 필요합니다.
- CNI 플러그인은 컨테이너 네트워크를 생성·연결·삭제하고, 삭제 시 할당한 자원을 정리합니다.
- Overlay Network는 물리 네트워크 위에 가상 네트워크를 구성하여 여러 Node의 Pod를 연결합니다.
- Kubernetes의 기본 네트워크 구성만으로는 다중 Node 통신이나 네트워크 정책 같은 고급 기능이 제한될 수 있으므로, CNI 사양을 준수하는 네트워크 플러그인을 사용합니다.

#### Kubernetes에서 사용하는 CNI 플러그인

- Flannel
- Calico
- Cilium
- Multus
